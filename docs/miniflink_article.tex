\title{miniFlink: Declarative Stream Processing Semantics in OCaml}

\author{miniFlink Project}
\date{}


\begin{document}
\maketitle

\begin{abstract}
We present miniFlink, a functional implementation of Apache Flink semantics
in OCaml that demonstrates how declarative stream processing reduces
accidental complexity. The key insight is the \texttt{KEYED} type class:
by encoding the grouping key once in the type, operators \texttt{window},
\texttt{enrich}, and \texttt{dedup} require no explicit \texttt{\textasciitilde{}key:}
parameter, making the pipeline read as a specification rather than
an implementation. We implement event time, watermarks (with periodic
emission, end-of-stream flush, and wall-clock idle advancement),
windowing in five flavors (tumbling, sliding, count, session with
merging, and a global window with custom triggers) with both
materializing and incremental ($O(1)$-memory) aggregation plus a
library of composable aggregators, stateful
operators, exactly-once checkpointing (single-thread and parallel via
Chandy-Lamport barrier snapshots, with source-offset recovery and a
transactional sink), table and join semantics with TTL eviction,
retractions and atomic updates for late data, and production layers
(dead letter queue with retry/backoff, graceful shutdown, Prometheus
metrics, structured logging, health and config as values, RocksDB-backed
persistent state via C FFI). A second design contribution is
\emph{orthogonal persistence}: every stateful operator runs unchanged
with or without durability, the mode being selected from outside the
pipeline through an ambient runtime context, with serialization handled
by default and never appearing in operator code. The library is
approximately 5{,}600 lines across 42 modules with 37 interface files;
it is validated by 120 test suites, of which 15 are property-based
(63 QCheck invariants with independent oracles) covering retract/update
consistency, FSM invariants, and crash-recovery transparency, alongside
replay-determinism, fuzzing, and soak tests. The test code (about
12{,}500 lines) exceeds the library itself by more than a factor of two.
A parallel backend supports both OCaml~4 (Thread + Mutex)
and OCaml~5 (Domain + Atomic) with measured speedup of $2.48\times$ on
4 workers and $2.87\times$ on 8 (OCaml~4, bounded by the runtime lock).
\end{abstract}


%%% ── 0. Declarativity ────────────────────────────────────────────────────
\section{Declarativity as a First Principle}

Traditional stream processing frameworks require the programmer to
explicitly state how to group events, how to serialize them, and how to
handle null values at every operator. Consider the same pipeline in
Kafka Streams (Java) and miniFlink (OCaml):

\begin{lstlisting}[caption={Kafka Streams (Java) — imperative},label={lst:kafka}]
KStream<String, Telemetry> stream =
    builder.stream("vehicles.telemetry");
KGroupedStream<String, Telemetry> grouped = stream
    .filter((k, v) -> v != null)
    .groupBy((k, v) -> v.getDeviceId(),
             Grouped.with(Serdes.String(), telemetrySerde));
KTable<Windowed<String>, Stats> stats = grouped
    .windowedBy(TimeWindows.ofSizeWithNoGrace(
                    Duration.ofSeconds(30)))
    .aggregate(Stats::empty,
               (k, v, acc) -> acc.add(v),
               Materialized.as("stats-store"));
stats.toStream()
    .flatMapValues(Rules::check)
    .filter((k, v) -> v != null)
    .to("fleet.alerts");
\end{lstlisting}

\begin{lstlisting}[caption={miniFlink (OCaml) — declarative},label={lst:mf}]
let pipeline source =
  source
  |> Event.with_watermarks   ~latency:(seconds 3)
  |> Pipe.enrich (module Telemetry)
       ~from:devices
       ~merge:(fun t dev -> { t with device = dev })
  |> Pipe.window (module Telemetry) (tumbling (seconds 30))
  |> Pipe.aggregate              Rules.compute
  |> Pipe.flat_map               (Rules.check Rules.fleet)
  |> Pipe.dedup (module Alert)
       ~rule:(fun a -> a.rule)
       ~cooldown:(minutes 5)
\end{lstlisting}

The differences are structural, not cosmetic:

\begin{itemize}
\item \textbf{No \texttt{key\_by}.} The \texttt{KEYED} type class encodes
  the grouping key in the type once; \texttt{window}, \texttt{enrich},
  and \texttt{dedup} extract it automatically.
\item \textbf{No type annotations} inside the \texttt{|>} chain.
  Hindley-Milner inference propagates types through all operators.
\item \textbf{No null checks.} \texttt{Option} makes absence explicit;
  \texttt{None} cannot be dereferenced.
\item \textbf{Format in one place.} Changing JSON to Protobuf means
  replacing one \texttt{Codec} value; the pipeline is untouched.
\end{itemize}

\section{Architecture}

miniFlink is organized into four orthogonal layers. Each layer depends
only on layers below it; the core never imports reliability or
parallelism modules.

\begin{table}[h]
\centering
\caption{Layer organization}
\begin{tabular}{lll}

%%% ── 2. Core Abstractions ────────────────────────────────────────────────
\section{Core Abstractions}

\subsection{Pull Stream}

\begin{lstlisting}
type 'a t = unit -> 'a option
\end{lstlisting}

A stream is a function. The call stack \emph{is} the operator graph.
No callbacks, no threads, no allocation per event beyond the value
itself. \texttt{map}, \texttt{filter}, \texttt{flat\_map} compose
without intermediate buffers.

\subsection{Event}

\begin{lstlisting}
type 'a t =
  | Data      of 'a * timestamp   (* value + event time *)
  | Watermark of timestamp        (* lower bound on future ts *)
  | Retract   of 'a * timestamp   (* revocation of prior Data *)
\end{lstlisting}

All three constructors flow through the same stream. Operators
match exhaustively — adding a constructor forces all operators
to handle it at compile time.

\subsection{KEYED Type Class}

\begin{lstlisting}
module type S = sig
  type t
  val key : t -> string
end

(* Registered once per domain type *)
module Telemetry = Keyed.Make(struct
  type t = telemetry
  let key t = t.device_id
end)
\end{lstlisting}

Operators receive \texttt{(module Telemetry)} as a first-class module
and call \texttt{K.key} internally. The user never writes
\texttt{\textasciitilde{}key:(fun t -> t.device\_id)} again.

\subsection{Window}

The locally abstract type annotation breaks the occurs-check that
would otherwise create the recursive type
$\alpha = \mathtt{string} \times \alpha\ \mathtt{list}$:

\begin{lstlisting}
let window (type a) ?(latency=0)
    ~(key : a -> string) spec
    (upstream : a Event.t Stream.t)
    : (string * a list) Event.t Stream.t = ...
\end{lstlisting}

Window state is a \texttt{WMap.t} from \texttt{(key, start, stop)}
triples to event lists. Watermarks trigger partition of open windows
into \emph{closed} (fired) and \emph{open} sets; closed windows emit
their accumulated events downstream.

Beyond time-based \texttt{tumbling} and \texttt{sliding}, miniFlink
offers three more window types as separate operators. \textbf{Count
windows} fire by event count rather than time, needing no watermarks.
\textbf{Session windows} have data-driven boundaries: a session grows
while events arrive within \texttt{gap} and \emph{merges} with a
neighbor when an event bridges the gap between two sessions — this
breaks the ``window is a pure function of timestamp'' assumption the
time-based windows rely on, so it carries its own session state and
merge logic. \textbf{Global windows} hold one window per key and
delegate the fire decision to a pluggable \emph{trigger}
($\mathtt{Continue} \mid \mathtt{Fire} \mid \mathtt{FireAndPurge}$),
separating the assigner (how to group) from the trigger (when to emit)
— the foundation other firing policies build on.

Aggregation over windows comes in two forms. The materializing path
(\texttt{window |> aggregate}) keeps the full event list and folds it
post-hoc — $O(n)$ memory per window. The incremental path
(\texttt{window\_fold \textasciitilde{}init \textasciitilde{}add})
folds each event into an accumulator on arrival — $O(1)$ memory in the
event count. On top sits a small library of composable aggregators
(\texttt{Agg}): \texttt{count}, \texttt{sum}, \texttt{mean},
\texttt{min\_by}/\texttt{max\_by}, \texttt{arg\_min}/\texttt{arg\_max},
etc. An aggregator hides its accumulator type behind a GADT
existential, so aggregators with different accumulators combine
uniformly; \texttt{both} (and an applicative \texttt{let+}/\texttt{and+})
compute several aggregates in a single pass. Feeding such an aggregator
to a window (\texttt{window\_agg}) requires applying the hidden
accumulator inside \texttt{window\_fold}; this is done with a rank-2
continuation (a record with a universally-quantified field) so the
existential accumulator type does not escape its scope — a small but
genuine use of the GADT/rank-2 combination, not decoration.

\subsection{Timers and ProcessFunction}

Windows react to events that \emph{arrived}; timers react to events
that \emph{did not}. \texttt{Pipe.process\_keyed} provides per-key
state plus two timer kinds: \emph{event-time} timers fire when the
watermark passes their time (deterministic, data-driven), and
\emph{processing-time} timers fire by wall clock — required for
``source went silent'' detection, where by definition no data drives
the watermark. Handlers \texttt{on\_event} and \texttt{on\_timer}
receive a context for emitting and for setting/cancelling timers.

Two semantic guarantees matter for composition. Emissions carry real
time (the timer's fire time from \texttt{on\_timer}, the event's
timestamp from \texttt{on\_event}) and leave the operator \emph{before}
the watermark that triggered them, so the output stream preserves
watermark monotonicity and can be fed into downstream windows. Timers
are checked as events and watermarks pass through the operator (pull
model, no background thread); a fully silent stream therefore needs
idle watermarks to keep time moving.

Timers live in operator memory and do not survive a restart, while
keyed state does (via checkpoints). The supported recovery pattern is
re-registration: keep \texttt{last\_seen} in state and, on startup,
re-register timers from the state snapshot;
\texttt{set\_event\_timer\_for} registers a timer for an arbitrary key
for exactly this purpose. NEXMark q3 (incremental person--auction join
with state expiry) is implemented on this primitive in the test suite.

%%% ── 3. Event Time and Watermarks ───────────────────────────────────────
\section{Event Time and Watermarks}

Each event carries its origin timestamp independently of processing
time. \texttt{with\_watermarks\_ext \textasciitilde{}latency ?interval}
inserts \texttt{Watermark(max\_seen - latency)}. The invariant:

\[
  \forall t < \mathtt{wm}:\ \text{no future } \mathtt{Data}(\_,\, t)
  \text{ will arrive}
\]

This allows deterministic window closure without wall-clock polling.
Watermarks are monotone by construction — \texttt{max\_seen} is a
\texttt{ref} that only grows.

Two refinements over naive per-event emission. \textbf{Periodic
emission:} the optional \texttt{\textasciitilde{}interval} parameter
emits a watermark only once it has advanced by at least
\texttt{interval} in event-time, collapsing the one-watermark-per-event
flood that a monotone stream would otherwise produce. \textbf{Final
flush:} on stream end the operator emits a terminal watermark equal to
\texttt{max\_seen} (without subtracting latency), guaranteeing every
trailing window closes rather than lingering open. A subtle integer
overflow — \texttt{wm - last\_wm} with \texttt{last\_wm = min\_int} —
is special-cased so the first watermark is never suppressed.

%%% ── 4. Exactly-Once ─────────────────────────────────────────────────────
\section{Exactly-Once Checkpointing}

\textbf{Single-thread.} A checkpoint is a triple $(epoch, offset, state)$.
The runner reads $N$ events, and on failure restores state from the
latest checkpoint, seeks the source to \texttt{offset}, and resumes.
The key invariant is \emph{ordered commit}: flush sink before writing
the checkpoint; write the checkpoint before committing the source
offset. Violated ordering creates either duplicates (checkpoint before
flush) or gaps (offset before checkpoint).

\textbf{Parallel (Chandy-Lamport).} For data-parallel execution,
\texttt{Checkpoint\_parallel} integrates barriers into the worker
channels. Channel messages are wrapped as
\texttt{Event of \_ | Barrier of epoch}. The dispatcher injects a
\texttt{Barrier(epoch)} into every worker channel every
\texttt{checkpoint\_every} events. On receiving a barrier each worker
snapshots its own \texttt{state\_backend} and submits
$(worker, epoch, bytes)$ to the coordinator. The coordinator commits
$\mathtt{checkpoint}(epoch)$ — the array of per-worker snapshots —
atomically once {\it all} workers have reported (barrier alignment;
trivial here since each worker has a single input channel). Because
key-sharding routes each key to exactly one worker, a committed
checkpoint is a consistent cut with no cross-worker double-counting.

\textbf{The offset-consistency pitfall.} The source offset stored in a
checkpoint must be \emph{consistent with the snapshotted state}. The
obvious implementation — record the dispatcher's source position at
barrier injection — is subtly wrong: the dispatcher reads ahead of what
workers have processed, so it may record \texttt{offset=2000} while the
snapshots reflect only 1900 processed events (the other 100 still in
flight in channels). On recovery the source would seek to 2000 and those
100 events would be lost — neither in state nor replayed. The fix: the
offset is the \emph{sum of per-worker processed counts captured at the
barrier}, taken in the same instant as each snapshot. Offset and state
are then consistent by construction; the discrepancy is physically
impossible. This bug passed functional tests and surfaced only under a
consistency check (offset must equal restored state count) — a concrete
illustration of why exactly-once demands invariant testing, not just
``does it work'' testing.

\textbf{Transactional output.} State-side exactly-once is not enough:
replaying the tail after recovery re-runs events through the sink.
miniFlink offers two paths. \emph{Idempotent}: results carry a
deterministic key and the sink upserts — a replay overwrites with the
same value, harmless, no transactions needed (ideal when the output is
``state'' rather than an event log). \emph{Two-phase commit}: results are
written to a per-epoch pre-commit buffer, made visible by
\texttt{ts\_commit} only when that epoch's checkpoint commits, and
rolled back by \texttt{ts\_abort} on failure — bound to the same barrier
that commits state. 2PC fits only sinks that separate write from
visibility (Kafka transactions, RDBMS, file staging+rename); for HTTP or
notifications, idempotency is the only option. A final \texttt{ts\_flush}
publishes the post-last-barrier tail at clean shutdown.

Together — consistent snapshot, offset = $\Sigma$ processed, durable
checkpoint store (atomic \texttt{rename} of a \texttt{LATEST} pointer),
recovery that seeks the source, and a transactional/idempotent sink —
these close end-to-end exactly-once on a single node. A dedicated
deep-dive is in \texttt{docs/exactly\_once.md}. Coordinating a real
external source/sink (Kafka \texttt{transactional.id}) and multi-input
barrier alignment remain out of scope.

%%% ── 5. Table and Join ───────────────────────────────────────────────────
\section{Table and Join}

\begin{lstlisting}
type ('k,'v) table = 'k -> 'v option

let of_list pairs = Hashtbl.find_opt (Hashtbl.of_seq ...)
let of_stream ~key src = fun k -> pump src; Hashtbl.find_opt h k
\end{lstlisting}

A table is a function. \texttt{Snapshot} tables call \texttt{pump}
on each lookup to drain pending updates from an upstream stream.
\texttt{lookup\_join} is a one-liner:

\begin{lstlisting}
let lookup_join (module K) ~from ~merge upstream =
  emap (fun v -> merge v (from (K.key v))) upstream
\end{lstlisting}

\texttt{interval\_join} buffers both streams; events match when
keys are equal and $|t_A - t_B| \leq \mathtt{window\_ms}$. The
combined watermark is $\min(\mathtt{wm}_A,\, \mathtt{wm}_B)$.

\texttt{of\_stream} is bounded by the number of {\it distinct} keys
(it uses \texttt{replace}, not \texttt{add}), but an unbounded key
space would still grow it without limit. For that case
\texttt{of\_stream\_ttl \textasciitilde{}key \textasciitilde{}ttl}
stores $(value, last\_ts)$ per key, tracks the maximum event-time
seen, and evicts any key whose $last\_ts < \mathtt{max\_ts} - ttl$ on
each pump — the same watermark-driven eviction used by \texttt{dedup},
bounding table size under a growing key space.

\subsection{Temporal (As-Of) Join}

The snapshot/live tables above answer ``what is the current value of the
dimension''. A \emph{temporal} join answers ``what was the value
\emph{as of} the row's event-time'' --- the Flink
\texttt{FOR SYSTEM\_TIME AS OF} semantics. The dimension is a
\emph{versioned} table: per key, a history of $(valid\_from, value)$ kept
sorted, so a late update with an old \texttt{valid\_from} is inserted in
its correct place. \texttt{as\_of k ts} returns the version with the
largest $valid\_from \leq ts$.

\begin{lstlisting}
let temporal_join ~key_main ~key_upd ~valid_from ~merge ~updates main =
  (* main event at T held until updates-watermark >= T, then
     enriched with as_of(key, T) *)
\end{lstlisting}

Correctness under \emph{late} updates is the whole point, and it rests on
watermarks exactly as elsewhere: a main event at time $T$ is
\emph{buffered} until the updates stream's watermark reaches $T$. Only
then are all updates with $valid\_from \leq T$ guaranteed to have arrived
--- including ones that were delayed in transit --- so \texttt{as\_of}
returns the correct version. This converts the arrival race into a
deterministic event-time result: the output is identical regardless of
the order in which rows and updates physically arrive. The cost is the
usual event-time trade-off --- buffering adds latency and memory, and a
silent updates stream stalls the watermark (addressed separately by
idle-watermarks). The guarantee is only as strong as the updates
watermark's promise that no earlier-stamped update is still coming.

%%% ── 6. Retractions ──────────────────────────────────────────────────────
\section{Retractions for Late Data}

When a late \texttt{Data} arrives after a window has fired, the
operator emits:
\[
  \mathtt{Retract}(v_\text{old},\, t) \;\to\; \mathtt{Data}(v_\text{new},\, t)
\]

Two aggregator strategies:

\begin{description}
\item[INVERTIBLE] $\mathtt{remove}(\mathtt{acc}, x)$ is defined.
  Late data: $O(1)$ update via \texttt{add}/\texttt{remove}.
  Examples: sum, count, average.
\item[RECOMPUTE] No inverse. Late data triggers full recomputation
  over the buffered event list: $O(n)$.
  Examples: max, min, percentile.
\end{description}

Both strategies produce identical external behaviour: the downstream
sees a \texttt{Retract}/\texttt{Data} pair and can perform an upsert.

%%% ── 7. Orthogonal Runtime ───────────────────────────────────────────────
\section{Orthogonal Runtime}

Each production capability has three files:
\texttt{foo.mli} (contract), \texttt{foo\_noop.ml} (zero-overhead stub),
\texttt{foo\_default.ml} (production implementation).
\texttt{runtime.ml} assembles them by \texttt{mode}:

\begin{lstlisting}
type mode = Noop | Log | Parallel | Prod

(* Noop: zero overhead, for tests *)
(* Log:  stderr metrics + SIGTERM handler *)
(* Prod: Prometheus HTTP :9090 + shutdown + DLQ log *)
\end{lstlisting}

\textbf{Dead Letter Queue.} \texttt{safe\_decode} wraps every codec
call; decode errors send the raw bytes to the DLQ with topic, error
message, and timestamp instead of crashing the pipeline.

\textbf{Graceful Shutdown.} A \texttt{guarded\_source} checks
\texttt{is\_requested()} before each poll. On SIGTERM: source returns
\texttt{None}, pipeline drains its buffer, sink flushes, process exits.

\textbf{Prometheus Metrics.} \texttt{metrics\_log} implements
counter, gauge, and histogram (7 buckets, $1\mu s$--$1s$) with
thread-safe \texttt{Mutex}-protected state and a TCP HTTP server
that serves the exposition text format on \texttt{GET /metrics}.

%%% ── 8. Parallelism ──────────────────────────────────────────────────────
\section{Parallelism}

Data parallelism via key sharding: \texttt{hash(key) mod N} routes
each event to a dedicated worker. Workers share no state — window
correctness follows from the invariant that all events for a given
key go to the same shard. The hash uses \texttt{land max\_int} (not
\texttt{abs}, which returns \texttt{min\_int} for \texttt{min\_int})
to guarantee a non-negative shard index.

\textbf{Crash resilience.} A worker body is wrapped in
\texttt{try/with}; on an exception it marks itself failed and closes
its input channel. The dispatcher uses \texttt{try\_push} (returning
\texttt{false} on a closed channel) and skips failed shards, so a
single worker crash can no longer deadlock the whole pipeline by
blocking the dispatcher on a full channel that nobody drains.

\textbf{Per-worker sinks.} \texttt{run\_parallel\_simple} takes an
optional \texttt{\textasciitilde{}sink\_factory : int -> 'b -> unit}.
When supplied, each worker writes to its own sink (e.g. its own Kafka
partition) with zero lock contention; otherwise a single shared sink is
guarded by a mutex. This removes the global-mutex bottleneck that
flattened throughput at high worker counts.

\begin{table}[h]
\centering
\caption{Benchmark: 1M events, 1000 devices, tumbling 30s, OCaml~4, 1 CPU}
\begin{tabular}{lrrr}
\toprule
Mode & ev/s & Time (s) & Speedup \\
\midrule
Sequential    & 209{,}293 & 4.78 & 1.00$\times$ \\

The sub-linear speedup on 1 CPU is expected: OCaml~4's GIL prevents
true parallelism, but channel-mediated pipelining hides latency.
On OCaml~5 with \texttt{Domain}, channel overhead drops from
$\sim$106\,ns (Mutex) to $\sim$30\,ns (Atomic), and real
4-core parallelism is expected to yield $3.5$--$3.8\times$.

%%% ── 9. Persistent State ────────────────────────────────────────────────
\section{Persistent State}

The \texttt{state\_backend} contract (\texttt{get}/\texttt{set}/%
\texttt{delete}/\texttt{snapshot}/\texttt{restore}) has three
implementations: \texttt{\_noop}, \texttt{\_memory} (Hashtbl), and
\texttt{\_rocksdb} backed by RocksDB through a C FFI. The FFI binds
\texttt{rocksdb\_open/put/get/delete} from the RocksDB C API. GC
safety is maintained by copying all bytes across the OCaml$\leftrightarrow$C
boundary immediately — the \texttt{get} stub \texttt{memcpy}s the
returned buffer into a fresh OCaml string and frees the C buffer before
returning, so no OCaml pointer is ever retained on the C side. The
\texttt{rocksdb\_t} handle lives in a custom block whose finalizer
closes the database. State persists across process restarts, verified
by a test that writes, closes, reopens the same path, and reads the
values back.

\subsection{Orthogonal Persistence}

The backend above answers \emph{where} state is stored. A second,
independent question is \emph{whether} a given pipeline persists at
all --- and the central design goal is that answering it requires
\emph{no change to the pipeline}. The same operator graph must run
identically with durability and without it; persistence and
serialization are deployment decisions, not properties of operators.

Two notions realize this. A \texttt{Runtime\_context} is an ambient
policy, installed for a dynamic extent by \texttt{with\_context}:
either \texttt{Ephemeral} (state lives in memory, nothing is written)
or \texttt{Durable} (state is snapshotted to a
\texttt{Persistence\_backend} and restored on start). A
\texttt{Managed\_state} is the keyed state an operator uses in place
of a bare \texttt{Hashtbl}: on creation it reads the ambient context
and, when durable, restores its entries from the backend by name
prefix; its \texttt{checkpoint} is a no-op under \texttt{Ephemeral},
so operators call it unconditionally and follow a single code path in
both modes.

\begin{lstlisting}
let pipeline src =
  src |> window_agg (module K) (tumbling 60000) (mean speed)
      |> Trigger.of_stream alert_spec

(* no persistence *)  pipeline source
(* with persistence *)
  with_context (durable backend) (fun () -> pipeline source)
\end{lstlisting}

Serialization is orthogonal as well. Operator state is closure-free
data, so \texttt{Marshal} serializes it automatically; the default
durable context needs no user-supplied codecs, which is ideal for
crash recovery (the same binary writes and reads the same format).
For schema evolution across deployments a name-keyed codec registry
can be supplied in the context, again without touching the pipeline.
All four stateful operators (windowed fold, \texttt{process\_keyed},
silence-age, and the trigger FSM) use this model; migrating them
removed roughly 1{,}800 lines of per-operator persistence machinery
--- bespoke JSON codecs, save/restore loops, and key parsing that each
operator had reimplemented.

A subtlety worth recording is key derivation. An earlier version
derived the string state key with \texttt{Hashtbl.hash}, a 30-bit
hash; two distinct keys could collide and collapse their state
machines into one slot, silently corrupting state. The fix keys by a
128-bit digest (\texttt{Marshal} then MD5), deterministic and
collision-free at any realistic key count. This is the kind of defect
that example-based tests miss and property-based tests catch
(Section~10).

%%% \u2500\u2500 10. Testing ─────────────────────────────────────────────────────────
\section{Testing}

\textbf{Harness.} A deterministic test context \texttt{('a,'b) t}
feeds events via \texttt{push}/\texttt{push\_wm} and collects
output via \texttt{run}. No broker, no threads, no wall clock.

The suite comprises 120 test executables run under
\texttt{dune test}; the test code (about 14{,}000 lines) is more than
twice the size of the library. Beyond operator-correctness unit tests
and the property tests below, the suite targets the failure modes
specific to stream engines:

\begin{description}
\item[Determinism] replay determinism (same input twice yields
  byte-identical output); parallel result equals sequential as a
  {\it multiset} (order between keys is nondeterministic by design, so
  multisets are compared — this proves key-sharding neither drops nor
  duplicates); watermark fuzzing on randomly time-shuffled streams;
  permutation invariance of order-independent aggregates.
\item[Exactly-once parallel] a checkpoint commits one snapshot per
  worker; state is restored after a simulated restart; exactly $n$
  outputs for $n$ inputs.
\item[Crash resilience] a watchdog-timed test crashes one worker and
  asserts the others still finish — without the fix it hangs.
\item[Soak] a separate slow target runs millions of events and asserts
  live heap growth $\leq 3\times$ (a leak would be $\sim 10\times$),
  validating dedup and window eviction.
\end{description}

\textbf{Property tests.} Fifteen property suites (63 QCheck
invariants, with thousands of generated cases each) check general laws
rather than specific inputs. Every property is checked against an
\emph{independent oracle} --- a separate, simpler computation of the
expected answer --- rather than a restatement of the implementation,
and the bug-finding ones were validated by sabotage: the operator is
deliberately broken, the property is confirmed to fail with a
counterexample, and the operator is then restored.

A first group establishes structural laws on append-only streams:
windows preserve all events ($\sum_w \mathtt{count}(w) = |\mathtt{input}|$),
\texttt{dedup} is idempotent, watermarks are monotone for any event
order, and \texttt{map}/\texttt{filter} preserve or shrink the event
count as expected.

A second, larger group targets the retract/update and persistence
semantics that example-based tests structurally miss:

\begin{enumerate}
\item \textbf{Aggregate retraction.} For a retractable aggregate, an
  arbitrary add/remove sequence equals the batch aggregation of only
  the remaining (non-retracted) elements --- for count, sum, mean,
  count-if, to-list, median, and combined aggregates.
\item \textbf{Window retraction.} For an arbitrary Data+Retract
  stream, a window's final value equals the batch aggregate of the
  elements remaining in that window. Sabotaging the open-window
  retract path makes this fail immediately.
\item \textbf{Update equivalence.} For the stateless combinators and
  their exception-safe variants, an atomic $\mathtt{Update}\,(o
  \to n)$ is equivalent to $\mathtt{Retract}(o)$ followed by
  $\mathtt{Data}(n)$, compared as multisets of normalized output. This
  property caught a real asymmetry in \texttt{safe\_filter} that
  manual review had missed.
\item \textbf{Trigger FSM.} With no debounce the trigger is a
  deterministic per-key state machine: active alerts equal the keys
  whose latest value crosses the threshold, retractions never exceed
  prior alerts, and at most one alert is active per key.
\item \textbf{Timers and counters.} A \texttt{process\_keyed} counter
  matches an oracle, and an event-time timer fires exactly once when
  the watermark passes it.
\item \textbf{Crash-recovery transparency.} For an arbitrary stream
  and an arbitrary crash point, a durable run --- phase one, crash,
  phase two on a shared backend --- yields the same per-window result
  as a continuous ephemeral run. Sabotaging the restore loop makes the
  property fail.
\end{enumerate}

%%% ── 10. Conclusion ──────────────────────────────────────────────────────
\section{Conclusion}

miniFlink demonstrates that the core semantics of Apache Flink —
event time, watermarks, windowing (five types including session with
merging and a trigger-driven global window), stateful operators,
exactly-once (single-thread and parallel via barrier snapshots, with
recovery and a transactional sink), table/join with TTL eviction,
retractions, and production layers (DLQ with retry, graceful shutdown,
Prometheus metrics, structured logging, health/config, RocksDB-backed
state) --- fit in roughly 5{,}600 lines of OCaml, validated by 120 test
suites whose code more than doubles the size of the library. Three
design decisions proved most consequential:

\begin{enumerate}
\item The \texttt{KEYED} type class eliminates repeated key
  extraction, making the pipeline read as a specification.
\item The \texttt{(type a)} locally abstract type annotation in
  \texttt{Pipe.window} avoids the recursive type $\alpha = \mathtt{string}
  \times \alpha\ \mathtt{list}$ that otherwise requires \texttt{Obj.magic}.
\item Orthogonal persistence --- an ambient \texttt{Runtime\_context}
  plus per-operator \texttt{Managed\_state} --- lets one pipeline run
  with or without durability unchanged, keeping persistence and
  serialization out of operator code entirely.
\end{enumerate}

The OCaml module system's ability to accept modules as runtime values
(first-class modules) is what makes both design decisions expressible
without metaprogramming or code generation.

Deliberate non-goals keep the ``mini'' honest: distributed execution,
remote shuffle, and incremental (delta) checkpointing are out of scope.
End-to-end exactly-once is supported on a single node through
source-offset recovery and a transactional sink, but not across a
distributed external source/sink. The project targets the
{\it semantics} of stream processing on a single node, not the
distributed infrastructure of a production cluster.

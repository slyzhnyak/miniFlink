# Нагрузочный тест после раундов 4-5 — июнь 2026

Проверка что изменения раундов 4-5 (efilt, window_agg noop-
suppression, group_by) не просадили производительность и не внесли
утечек на масштабе.

## Найдена и устранена регрессия: group_by Hashtbl.copy

Round-5 фикс корректности (group_by с immutable acc) использовал
Hashtbl.copy на каждом add/remove. Нагрузочный тест на 4096-лампном
ex07 median_rssi показал заметную цену:

| Вариант group_by            | median_rssi время | alloc | Корректность |
|-----------------------------|-------------------|-------|--------------|
| mutable Hashtbl (был БАГ)    | 0.30с             | 522МБ | теряет late  |
| Hashtbl.copy (round-5 fix)  | 0.43с (+43%)      | 649МБ | OK           |
| **immutable Map (текущий)** | **0.35с (+17%)**  | 556МБ | OK           |

Заменил Hashtbl на immutable Map (Map.Make(String)). Map.add —
O(log n) со структурным разделением (переиспользует неизменённые
ветки дерева вместо полного копирования), поэтому add/remove
естественно возвращают независимый снимок дёшево. Восстановило
бóльшую часть регрессии при полной корректности.

Остаточные +17%/+7% против багованного mutable — неизбежная цена
корректности (персистентное обновление O(log n) вместо
деструктивного O(1)).

## Полный прогон на масштабе (4096 ламп)

ex07 median_rssi, Full config (16×64 биконов, 16×256=4096 шахтёров,
~950K пакетов):

- median_rssi: 53с, alloc 33ГБ, heap peak 2ГБ, 19K ev/s
- connectivity_alerts: 397K ev/s
- событий окон: 2.65M

Heap peak 2ГБ объясним sliding-window (60с/5с) на 4096 ключах —
много одновременно открытых окон. Не утечка (см. soak ниже), а
рабочий объём состояния.

## Таргетный бенч изменённых путей (bench_changed_paths)

На 1M событий:

| Путь                            | Время  | Alloc  | Результат          |
|---------------------------------|--------|--------|--------------------|
| efilt (mixed Update/Retract)    | 0.089с | 221МБ  | 740K passed (корр.)|
| group_by+late (200K окон)       | 4.3с   | 1.25ГБ | 200K real Updates  |

filter быстр и корректен на asymmetric Update. group_by даёт Update
на КАЖДОЕ late событие (200K из 200K) — Map-путь обрабатывает
коррекции без потерь.

## Soak: отсутствие утечек (soak_agg)

5M событий через group_by/window_agg/efilt с НЕПРЕРЫВНЫМИ late-data
коррекциями:

```
500000 -> 46 KB    3000000 -> 46 KB
1000000 -> 46 KB   3500000 -> 46 KB
...                ...
2500000 -> 46 KB   5000000 -> 46 KB
growth ratio: 1.00x   PASS
```

Heap идеально стабилен (46КБ на всех чекпойнтах). Подтверждает:
- group_by на Map не накапливается (старые окна освобождаются)
- window_agg noop-suppression не держит состояние
- efilt не течёт
- window purge по allowed_lateness работает

Базовый soak (window/dedup/enrich, 5M событий) — тоже 1.00x,
heap 57-76КБ.

## Параллельный путь (bench_parallel)

1M событий, 1000 устройств:
- Корректность: ВСЕ режимы (seq, 1/2/4/8 workers) дают идентичные
  167858 alerts — collector-fix раунда 3 не нарушил семантику, нет
  потерь/дублей при шардировании.
- Speedup: 8 workers → 1.40x. Скромно из-за OCaml 4.14 GIL (Thread,
  не настоящий параллелизм). На OCaml 5 (Domain, parallel_v5) было
  бы выше — архитектурное свойство, не регрессия.
- Channel: 8.6M msg/s (116 ns/msg).

## Вывод

Изменения раундов 4-5 проверены под нагрузкой:
- Корректность сохранена на масштабе (параллель даёт те же alerts).
- group_by-регрессия от Hashtbl.copy устранена переходом на Map
  (+17% против багованного, приемлемо за корректность).
- Утечек нет: 5M событий с непрерывными коррекциями → стабильный
  heap.
- Новые бенчи (bench_changed_paths, soak_agg) остаются для будущих
  регрессий.

Узкое место производительности — параллелизм на OCaml 4.14 (GIL).
Если minePASS упрётся в пропускную способность, путь — OCaml 5 +
parallel_v5 (Domain). Это решение про целевую версию, не баг.

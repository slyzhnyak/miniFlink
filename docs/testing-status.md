## Property-инварианты (62)

Property-тесты проверяют свойство для тысяч случайных входов, а не для
подобранных примеров. Каждый инвариант сверяется с независимым oracle и
прошёл sanity-проверку (намеренная поломка инварианта → тест падает),
чтобы исключить «пустое» прохождение.

Покрытые классы:

- **Алгебра агрегатов** — count/sum/mean/median/count_if/to_list с
  retract равны пересчёту с нуля; `both` согласован покомпонентно.
- **Update ≡ Retract+Data** — для map/filter/flat_map и их safe-версий.
- **Триггеры** — ≤1 активный алерт на ключ; retract не превышает
  предыдущие данные; активные алерты = ключи выше порога.
- **Окна** — `window_agg` (sum/count/mean) и `window_fold`
  инкрементально равны пересчёту; `sliding`-назначение накрывает ts,
  выровнено по step, число окон = oracle.
- **Watermark-монотонность (P-02)** — watermark на выходе `merge`
  никогда не убывает при любых партициях, включая переход
  «молчала → ожила с отставанием». Роадмап называет это самым важным
  инвариантом streaming-системы.
- **Temporal** — `as_of` = версия с максимальным `valid_from ≤ ts`;
  `prune` не меняет видимых ответов для `ts ≥ before`.
- **Прочие операторы** — `enrich` (left join), `session_window`
  (gap-разделение + сохранение событий), `update_table`
  (last-write-wins + passthrough), `dedup`, `keyed_join`,
  `process_keyed`, `silence_age`.

Операторы без property-инварианта — по сознательному решению: `stateful`
(нет универсального инварианта, зависит от пользовательской функции),
`keyed_join_map` (дублирует покрытый `keyed_join`), `count_window`
(близок к покрытому `tumbling`), `global_window` (сложный oracle,
средняя ценность).

## Закрытые риски

1. **cp_offset / exactly-once (review v3 §4.1) — ИСПРАВЛЕН** (HEAD
   `47f8934`). Долгое время главный незакрытый долг. Оказалось два
   связанных бага:

   - *Исходный §4.1:* `cp_offset` брался из числа обработанных Data, а
     `source.seek` ждёт индекс в полном потоке
     (Data+Watermark+Retract+Update). При watermark-ах между Data offset
     промахивался — повтор или потеря событий.
   - *Глубже (вскрылся при починке первого):* финальный барьер
     фиксировал «сколько разослано», а снапшот содержит «сколько
     обработано»; при in-flight событиях offset обгонял снапшот. На
     потоках из одних Data старый код был согласован случайно, поэтому
     наивный фикс «offset = позиция источника» чинил случай с watermark,
     но ломал all-Data (терял хвост при replay).

   **Решение:** координатор ведёт `data_positions` (k-е Data → позиция в
   потоке); `cp_offset = data_positions[snap_processed]` — позиция,
   соответствующая числу Data в снапшоте. Offset согласован со снапшотом
   независимо от watermark-ов и in-flight; старые записи чистятся на
   каждом коммите (память ограничена на long-running прогоне — важно при
   ~4096 лампах).

   **Проверено:** all-Data (2000), Data+Watermark (400),
   Data+Watermark+Retract — recovery+replay ровно по счёту без потерь и
   дублей, по 3 прогона каждый; crash-тесты ×3; полный набор зелёный; CI
   зелёный на OCaml 4.14 и 5.2. `test_cp_offset` переписан из
   xfail-заглушки в строгую регрессию (согласованность offset/снапшот И
   полный recovery+replay = n).

## Что осталось вне текущего охвата (по приоритету)

- **Exactly-once как property** — теперь разблокировано фиксом §4.1:
  можно проверять «recovery = бескрашевый прогон» для любых потоков
  property-тестом, а не точечными примерами.
- **Concurrency property-тесты** — систематическая проверка гонок;
  требует OCaml 5 / стресс-инфраструктуры (на OCaml 4 настоящего
  параллелизма нет). Частично разблокировано: offset-логика, на которую
  они опирались, теперь корректна.
- **Инфраструктурное покрытие** (Prometheus endpoint, reporter) —
  честнее закрывать интеграционными прогонами, а не юнит-тестами.

## Вывод

Тестовая база в хорошем состоянии: покрытие ~86 %, ядро под
property-инвариантами, CI зелёный на обеих версиях OCaml. Главный
исторический долг — корректность exactly-once при восстановлении
(§4.1) — закрыт и проверен на сценариях с watermark, retract, крашами и
in-flight событиями. Критических открытых рисков по корректности на
текущий момент нет; оставшиеся пункты (exactly-once и concurrency как
property) — это усиление проверок, а не незакрытые баги, и они
разблокированы для следующих итераций.

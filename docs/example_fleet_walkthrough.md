# Разбор примера ex05 — production-путь обработки потока

Подробный разбор [`examples/ex05_fleet.ml`](../examples/ex05_fleet.ml):
сквозной пример, который собирает вместе production-возможности miniFlink
на одном реалистичном сценарии. Документ идёт секция за секцией и
объясняет не только *что* делает код, но и *почему* именно так, где
проходят границы гарантий и какие компромиссы заложены.

Если ex04 (`ex04_mine.ml`) показывает **топологию** (несколько источников,
`union`, `enrich`, разные типы окон, `dedup`), то ex05 показывает
**production-стек**: устойчивость к беспорядку в данных, изоляцию сбоев,
exactly-once с восстановлением после краха, версионирование состояния и
операционную обвязку.

## Сценарий

Флот электробусов шлёт телеметрию: `(bus_id, depot, speed, charge, ts)`.
Данные приходят как в реальной жизни — **вперемешку по времени, с
опозданиями и дублями**, и часть показаний **битые** (сенсор сбоит).
Нужно по каждому депо посчитать в окнах: среднюю скорость, минимальный
заряд и число автобусов с низким зарядом — и сделать это так, чтобы
беспорядок и сбои не искажали результат.

Запуск:

```bash
dune exec examples/ex05_fleet.exe
```

## Карта примера

Пример делится на пять демонстраций, каждая под своей меткой в выводе:

| Метка | Что показывает | Ключевые API |
|-------|----------------|--------------|
| **[A]** | Корректность при беспорядке (опоздавшие, дубли, out-of-order) + изоляция битых | `safe_map`, `window_agg`, `Agg`, `allowed_lateness`, `of_list` |
| **[B]** | Exactly-once с восстановлением после краха процесса | `run_exactly_once`, `recover`, `make_store ~persist` |
| **[C]** | Версионированная сериализация состояния | `Schema_default` |
| **[D]** | Устойчивая запись во внешний приёмник | `Retry.with_retry` |
| **[E]** | Операционная сводка | `Health` |
| **[F]** | Слияние потоков + таблица из потока + дедупликация | `union`, `update_table`, `enrich`, `dedup` |
| **[G]** | Temporal join: депо на момент события, корректно при опоздавших апдейтах | `Temporal.temporal_join` |

## 1. Доменная модель и ключ группировки

```ocaml
type telemetry = {
  bus_id : string;
  depot  : string;       (* депо приписки — ключ группировки *)
  speed  : float;
  charge : float;        (* заряд %, 0..100 *)
  ts     : Time.t;
}

module ByDepot = Keyed.Make (struct
  type t = telemetry
  let key t = t.depot
end)
```

`Keyed.Make` — это способ задать «по какому полю группировать» один раз, в
типе, а не повторять `~key_by:(fun t -> t.depot)` в каждом операторе. Все
оконные операторы принимают `(module ByDepot)` и сами знают как извлечь
ключ. Это первоклассный модуль как type-class: группировка становится
частью типа потока, а не параметром каждого вызова.

---

## 2. Сырые данные: беспорядок намеренный

`raw` — это «как пришло с провода», ещё до валидации. Список `raw_events`
устроен специально недружелюбно, чтобы проверить движок на прочность:

- **out-of-order** — `r_ts` скачет: первым приходит событие на `t=2`,
  вторым — на `t=23` (это будущее окно `[20,30)`), потом снова ранние.
  Порядок в списке = порядок **прихода**; `r_ts` = настоящее
  **event-time**.
- **опоздавшие** — `B8 (t=3)`, `B9 (t=13)`, `B2 (t=7)` стоят в конце
  списка, хотя их время относится к ранним окнам. К моменту их прихода
  соответствующее окно по watermark уже закрылось.
- **дубли** — события с `t=2`, `t=5`, `t=23` присланы дважды (ретрай на
  той стороне прислал копию).
- **битые** — `B1 (t=4)` с зарядом `-1` (вне диапазона 0..100) и
  `B5 (t=14)` со скоростью `nan`.

> **Почему это реалистично.** В реальном потоке сеть, буферизация,
> переподключения и ретраи источника регулярно переставляют события,
> задваивают их и приносят с опозданием. Движок, который «работает только
> на чистых упорядоченных данных» — бесполезен. Весь смысл event-time
> семантики в том, чтобы давать **правильный** ответ несмотря на это.

## 3. Валидация как исключение

```ocaml
let validate (r : raw) : telemetry =
  if r.r_charge < 0. || r.r_charge > 100. then failwith "...charge out of range...";
  if Float.is_nan r.r_speed || r.r_speed < 0. then failwith "...invalid speed...";
  { bus_id = r.r_bus; depot = r.r_depot; speed = r.r_speed;
    charge = r.r_charge; ts = r.r_ts }
```

`validate` **бросает исключение** на битом показании. Это намеренно:
исключение — естественный способ для пользовательской функции сказать
«этот элемент обработать нельзя». Дальше его перехватит `safe_map`
(секция [A]). Заметьте, что та же `validate` используется и в EO-части
([B]) — там битые отфильтровываются заранее через `try ... with`.

## 4. Пайплайн агрегации (секция [A])

Это сердце примера. Пайплайн — композиция операторов через `|>`:

```ocaml
let pipeline source =
  source
  |> Pipe.safe_map ~on_error:(fun e -> incr dropped; Log.warn ... ) validate
  |> Mf_event.with_watermarks ~latency:(seconds 1)
  |> Pipe.window_agg (module ByDepot)
       ~latency:(seconds 1) ~allowed_lateness:(seconds 30)
       (Pipe.tumbling (seconds 10))
       Agg.(both (both (mean (fun t -> t.speed))
                       (min_by (fun t -> t.charge)))
                 (count_if (fun t -> t.charge < 20.)))
```

Разберём по слоям.

### 4.1. `safe_map` — изоляция сбоя на уровне одного события

```ocaml
|> Pipe.safe_map ~on_error:(fun e -> incr dropped; Log.warn ...) validate
```

Обычный `map` пробросил бы исключение из `validate` наружу и **уронил бы
весь поток** — одно битое показание убило бы обработку всего флота. Это
неприемлемо в проде, где битые события неизбежны.

`safe_map ~on_error f` ловит исключение из `f` на каждом событии,
вызывает `on_error exn` (здесь: инкремент счётчика + структурный лог) и
**пропускает** это событие — поток продолжается. Watermark и retract
проходят насквозь. Это прямой аналог пути `decode → DLQ` для
произвольной пользовательской функции.

В выводе: `битых пропущено: 2` — `B1(t=4)` и `B5(t=14)` отсеяны, остальные
16 событий обработаны.

### 4.2. `with_watermarks` — граница «прошлое закрыто»

```ocaml
|> Mf_event.with_watermarks ~latency:(seconds 1)
```

Watermark — это маркер в потоке, говорящий «событий с временем меньше
данного больше (почти) не будет». Окна закрываются по watermark, а не по
порядку прихода. `~latency:(seconds 1)` означает «watermark отстаёт от
максимально увиденного event-time на 1с» — допуск на небольшой
естественный беспорядок: событие, опоздавшее в пределах 1с, ещё застанет
своё окно открытым.

> **Тонкость.** Watermark **монотонен**: он только растёт. Когда после
> события `t=23` приходит `t=3`, watermark не откатывается назад — иначе
> уже закрытые окна «переоткрывались» бы хаотично. Сильно опоздавшие
> (больше `latency`) попадают в уже закрытое окно, и их судьба зависит от
> следующего параметра.

### 4.3. `window_agg` + `allowed_lateness` — окна по event-time и пересчёт опоздавших

```ocaml
|> Pipe.window_agg (module ByDepot)
     ~latency:(seconds 1) ~allowed_lateness:(seconds 30)
     (Pipe.tumbling (seconds 10)) <агрегатор>
```

- **`tumbling (seconds 10)`** — неперекрывающиеся окна по 10с: `[0,10)`,
  `[10,20)`, `[20,30)`. Событие попадает в окно **по своему event-time**,
  а не по моменту прихода. Поэтому `t=23`, пришедшее вторым, корректно
  уходит в `[20,30)`, а `t=2` — в `[0,10)`, независимо от перемешанности.
- **`allowed_lateness:(seconds 30)`** — ключ к обработке сильно
  опоздавших. После того как watermark закрыл окно, оно ещё `30с`
  (по event-time) принимает опоздавшие события. Когда такое приходит,
  окно **пересчитывает** агрегат и эмитит **retract** прошлого результата
  плюс новый. Так `B8(t=3)`, пришедшее в самом конце, всё равно попадает
  в `[0,10)` и поднимает там счётчики.

В выводе это видно по числам: `эмиссий окон: 11 | retract'ов: 7`. Семь раз
опоздавшее событие заставило окно пересчитаться (retract старого + новый).
Без `allowed_lateness` опоздавшие на закрытое окно просто терялись бы.

### 4.4. `Agg` — три метрики за один проход

```ocaml
Agg.(both (both (mean  (fun t -> t.speed))
                (min_by (fun t -> t.charge)))
          (count_if (fun t -> t.charge < 20.)))
```

Агрегатор — это инкрементальная свёртка (`init`/`add`/`finish`) со скрытым
аккумулятором. `both a b` считает оба агрегата **за один проход** по окну,
возвращая пару. Здесь вложенный `both (both mean min_by) count_if` даёт
результат типа `((float option * float option) * int)` — средняя скорость,
минимальный заряд и число «низкозарядных» одновременно, без трёх
отдельных обходов окна.

`window_agg` применяет агрегатор инкрементально поверх `window_fold`:
память на окно — O(1) по числу событий (хранится только аккумулятор, не
список). Подробнее об устройстве `Agg` (GADT-экзистенциал для скрытого
аккумулятора, rank-2 континуация чтобы тип не «убежал») — в технической
статье.

### 4.5. Доказательство корректности

Просто «получить какие-то числа» — мало. Пример **доказывает**, что
беспорядок не влияет на результат:

```ocaml
(* тот же набор событий, отсортированный по event-time *)
let in_order_sorted = List.stable_sort (fun a b -> compare a.r_ts b.r_ts) raw_events in
let in_order = final_windows (Mf_event.of_list ~ts:... in_order_sorted |> pipeline) in
Printf.printf "... тот же итог: %b ...\n" (out_of_order = in_order)
```

`final_windows` собирает **финальный** результат каждого окна, применяя
retract'ы (последняя эмиссия `(депо, конец_окна)` после всех пересчётов —
это и есть правильный итог). Затем те же события прогоняются
**отсортированными по event-time** через тот же пайплайн, и финальные
результаты сравниваются.

Вывод: `тот же набор в правильном порядке даёт тот же итог: true`. Окна
группируют по event-time, а не по порядку прихода — поэтому беспорядок во
входе не меняет ответ. Это и есть суть event-time семантики.

### 4.6. Что показывает вывод [A]

```
окно[..10s] депо north : ср.скорость 42.5 км/ч мин.заряд 11%   низкий заряд: 4
окно[..20s] депо north : ср.скорость 30.0 км/ч мин.заряд 55%   низкий заряд: 0
окно[..20s] депо south : ср.скорость 57.0 км/ч мин.заряд 8%    низкий заряд: 2
окно[..30s] депо south : ср.скорость 53.3 км/ч мин.заряд 90%   низкий заряд: 0
битых пропущено: 2 | эмиссий окон: 11 | retract'ов: 7
=== тот же набор в правильном порядке даёт тот же итог: true ===
```

Окно `[0,10)` north — это все валидные north-показания с временем в
`[0,10)`, **включая** опоздавшие `B8(t=3)`, `B2(t=7)` и дубли `t=2`, `t=5`:
скорости `42, 38, 44, 45, 38(дубль), 42(дубль), 50, 41` → среднее
`340/8 = 42.5`. Низкозарядных (charge < 20): `15, 12, 15(дубль), 11` → `4`.

> **Важно про дубли.** `mean` и `count_if` считают дубли как **отдельные
> события** — они не дедуплицируются автоматически. Это правильное
> поведение по умолчанию: движок не может знать, дубль это или два
> легитимных одинаковых показания. Если нужна дедупликация по
> бизнес-ключу — для этого есть отдельный оператор `Pipe.dedup`
> (см. ex02/ex04), который ставится в пайплайн до окна. То есть «итог
> совпадает с упорядоченным прогоном» означает **детерминизм по
> event-time**, а не «дубли исчезли».

## 5. Exactly-once с восстановлением (секция [B])

Здесь — отдельный путь: накопительная сумма скоростей по депо через
параллельный exactly-once движок, с имитацией краха процесса.

### 5.1. `process` — обработчик с состоянием по ключу

```ocaml
let eo_process backend ev =
  match ev with
  | Mf_event.Data (t, _) ->
    let cur = (* прочитать стейт депо из backend, декодировать схемой *) in
    let s' = { sum_speed = cur.sum_speed +. t.speed; n = cur.n + 1;
               min_charge = Float.min cur.min_charge t.charge } in
    State_backend_memory.set backend t.depot (Schema_default.encode stat_schema s');
    [(t.depot, s'.sum_speed, s'.n)]
  | _ -> []
```

Состояние живёт в `backend` (key-value), ключ — депо. Именно это состояние
checkpoint'ится и восстанавливается. Сериализуется оно через `schema`
(секция [C]) — версионированно.

### 5.2. Эталонный прогон

```ocaml
CP.run_exactly_once
  ~workers:1 ~capacity:64 ~checkpoint_every:3
  ~key_of:(fun t -> t.depot) ~make_state:State_backend_memory.create
  ~process:eo_process
  ~source:(CP.seekable_of_list events)
  ~sink:(CP.idempotent_sink collect)
  ~store ()
```

`run_exactly_once` шардирует события по `key_of`, обрабатывает их через
`process` на воркерах, периодически (`checkpoint_every`) делает
консистентный снимок состояния всех воркеров (Chandy–Lamport барьер) и
коммитит его в `store` вместе с offset источника. `idempotent_sink` —
приёмник, выдерживающий повторную доставку (на случай переигрывания после
recovery).

### 5.3. Имитация краха и восстановление

```ocaml
(* фаза 1: durable store, обработать половину, «умереть» *)
let store1 = CP.make_store ~persist:(fun cp -> durable := cp :: !durable) () in
CP.run_exactly_once ~workers:1 ... ~source:(seekable_of_list first) ~store:store1 ();

(* фаза 2: новый процесс — durable checkpoint-ы целы, recover *)
let store2 = CP.make_store () in
List.iter (CP.commit store2) (List.rev !durable);
let full = CP.seekable_of_list events in
let backends = CP.recover ~workers:1 ~make_state:... ~source:full store2 in
(* продолжить обработку с восстановленного offset *)
```

Идея: `~persist` пишет каждый checkpoint в «долговременное хранилище»
(`durable`), которое **переживает смерть процесса**. После «краха» новый
процесс создаёт свежий store, заливает в него durable checkpoint-ы, и
`recover` (1) восстанавливает состояние воркеров из последнего checkpoint
и (2) перематывает источник на сохранённый offset. Обработка продолжается
с этой точки.

Проверка: финальные суммы по депо после recovery сравниваются с
эталонным прогоном без сбоя:

```
checkpoint-ов в эталоне: 6
депо north  суммарная скорость: 370
депо south  суммарная скорость: 388
recovery == эталон: true
```

`recovery == эталон: true` — восстановление не потеряло и не задвоило
данные. Это практическая проверка главной гарантии движка.

> **Граница честности.** Это **single-node** exactly-once: консистентный
> снапшот операторного состояния + offset источника + идемпотентный sink.
> Полноценный end-to-end EO через внешние транзакционные источники и
> приёмники (как Kafka EOS) — вне области проекта (см. Non-goals в
> README). Пример показывает ровно то, что движок реально гарантирует.

## 6. Версионированная схема состояния (секция [C])

```ocaml
let stat_schema = Schema_default.make ~version:1
  ~encode:(fun s -> ...) ~decode:(fun b -> ... Ok {...} | Error "...") ()
```

`schema` оборачивает сериализацию состояния номером версии. Сейчас версия
1, но когда формат `depot_stat` изменится, `decode` сможет либо
мигрировать старые данные, либо вернуть явную ошибку на неизвестной
версии — вместо тихого чтения мусора. Для долгоживущего сервиса, чьё
состояние переживает деплои с изменением формата, это страховка от
порчи данных при апгрейде. В примере — простой round-trip
encode→decode для демонстрации контракта.

## 7. Устойчивая запись во внешний приёмник (секция [D])

```ocaml
ignore (Retry.with_retry Retry.default
  ~sleep:(fun _ -> ())
  ~on_give_up:(fun _e n -> Printf.printf "gave up after %d attempts\n" n)
  flaky_publish "depot=north avg=41")
```

`flaky_publish` имитирует нестабильный внешний приёмник: первые две
попытки бросают исключение, третья проходит. `Retry.with_retry` повторяет
с экспоненциальным backoff (здесь `~sleep` заглушён, чтобы пример не ждал
реально), и сдаётся через `max_attempts`, вызвав `on_give_up`. Вывод:
`(успех после 3 попыток)`. Так оформляется устойчивая доставка результатов
наружу — типичная «последняя миля» пайплайна.

## 8. Операционная сводка (секция [E])

```ocaml
let h = Health.check ~state_size:(fun () -> List.length events) () in
Printf.printf "%s\n" (Health.to_json h)
```

`Health.check` собирает снимок состояния сервиса (готовность, размер
состояния, лаг watermark, глубину очередей) в JSON для health-эндпоинта.
Это и подобные операционные слои (структурные логи, Prometheus-метрики,
graceful shutdown, config) — то, что отличает «алгоритм в вакууме» от
сервиса, который можно эксплуатировать.

> **Замечание об API.** Опции `Health.check` принимаются как **функции**
> (`~state_size:(fun () -> ...)`), а не как готовые значения — это ленивое
> вычисление, чтобы дорогие метрики считались только при опросе. Поначалу
> неинтуитивно (ожидаешь `~state_size:5`); это одна из шероховатостей API,
> которую видно именно при написании реального приложения, а не теста.

## 9. Stream-table join: union + update_table + enrich + dedup (секция [F])

Эта секция показывает, как несколько потоков соединяются, и как
**справочная таблица, наполняемая из потока и меняющаяся во времени**,
обогащает основной поток.

### 9.1. `union` — слияние двух источников

```ocaml
let city   = Mf_event.of_list ~ts:(fun t -> t.ts) city_buses in
let suburb = Mf_event.of_list ~ts:(fun t -> t.ts) suburb_buses in
let merged = Mf_event.union city suburb
```

Городские и пригородные автобусы шлют телеметрию раздельно; `union`
сливает два потока в один, упорядочивая по event-time. Watermark
объединённого потока — **минимум** watermark'ов входов: нельзя считать,
что время T прошло, пока *оба* источника это не подтвердили (иначе окна
закрылись бы преждевременно, потеряв данные медленного входа).

### 9.2. `update_table` — таблица, наполняемая из потока

```ocaml
let depot_of : (string, assignment) Hashtbl.t = Hashtbl.create 8 in
Mf_event.of_list ~ts:(fun a -> a.a_ts) assignments
|> Pipe.update_table depot_of ~key:(fun a -> a.a_bus)
|> Stream.to_list |> ignore;          (* прогнали — таблица наполнена *)
```

Приписка «автобус → депо» приходит **отдельным потоком назначений** и
**меняется во времени**: в данных `B1` сначала в `north`, а потом
(`a_ts = 100`) его переводят в `south`. `update_table` наполняет `Hashtbl`
по мере прохождения событий — события проходят насквозь, а побочный
эффект наполняет таблицу. Последнее назначение по ключу побеждает, поэтому
после прогона `B1 → south`.

> **Тонкость (важная).** `update_table` обновляет таблицу **по порядку
> прихода**, а не по event-time. В этом примере таблица сначала
> полностью наполняется (поток назначений прогоняется до конца через
> `Stream.to_list`), и только потом используется для enrich — то есть
> enrich видит **финальное** состояние справочника. Это «как есть сейчас»
> семантика, типичная для справочных данных: телеметрия `B1` обогащается
> текущим депо `south`, даже та, что по event-time была до перевода.
> Если нужна **темпоральная** привязка (депо на момент события), это
> отдельная, более сложная задача (versioned/temporal join), которую
> miniFlink из коробки не делает — и это честно: пример показывает
> snapshot-join, не temporal-join.

### 9.3. `dedup` — подавление дублей

```ocaml
|> Pipe.dedup (module ById)
     ~rule:(fun t -> string_of_int t.ts)   (* ключ дедупа: bus_id + время события *)
     ~cooldown:(seconds 60)
```

`dedup` подавляет повторные события с одинаковым `(K.key, rule)` в
пределах окна `cooldown` по event-time. Ключ здесь — `bus_id` (из модуля
`ById`) плюс `rule` = время события: два показания одного автобуса с
одинаковым event-time считаются дублем. В выводе: `union` дал 7 событий,
после dedup осталось 5 (убраны дубли `B3@3s` и `B2@4s`).

> **Почему cooldown=60s, а не 1s.** Это та же природа, что у
> `allowed_lateness`. `dedup` хранит «последний раз видел этот ключ» и
> вытесняет старые записи по watermark, чтобы состояние было ограничено.
> Если `cooldown` мал, а дубль приходит позже (после `union` дубли
> разнесены по позиции в потоке, и watermark между ними успевает
> вытеснить запись) — дубль «не вспомнится» и пройдёт. Значение `cooldown`
> должно покрывать ожидаемый разброс между оригиналом и его дублем во
> входном потоке. Тот же компромисс память↔полнота, что и везде в
> event-time системах.

### 9.4. `enrich` — обогащение из таблицы (left join)

```ocaml
let depot_table = Table.of_hashtbl depot_of in
...
|> Pipe.enrich (module ById)
     ~from:depot_table
     ~merge:(fun t assign -> match assign with
        | Some a -> { t with depot = a.a_depot }   (* подставили депо *)
        | None -> t)                               (* нет записи — как есть *)
```

`enrich (module K) ~from ~merge` для каждого события основного потока
ищет в таблице запись по ключу `K.key` и вызывает `merge событие
(запись option)`. Это **left join**: если записи нет (`None`), событие
проходит как есть. Здесь enrich подставляет в `telemetry.depot` актуальное
депо из таблицы приписки. В выводе видно, что вся телеметрия `B1`
обогащена как `south` — потому что таблица к моменту enrich уже отражает
перевод.

Полная цепочка секции: `union` (2 источника) → `with_watermarks` →
`dedup` (убрать дубли) → `enrich` (подставить депо из справочника) →
результат. Это типичный шаблон «слить входы, очистить, обогатить
справочными данными» — и в miniFlink он собирается из тех же маленьких
`|>`-операторов.

## 10. Temporal join: «как было на момент события» (секция [G])

Секция [F] делает **snapshot-join**: enrich видит таблицу в её финальном
состоянии, поэтому вся телеметрия `B1` получает депо `south` (последнее
назначение). Это правильно для вопроса «где автобус сейчас», но неверно
для вопроса «к какому депо относилось показание, снятое в момент `t=50`,
когда автобус ещё был в `north`».

`Temporal.temporal_join` отвечает именно на второй вопрос — **as-of
join**, и делает это корректно **даже если апдейт справочника пришёл с
опозданием**.

```ocaml
b1_readings
|> Mf_event.with_watermarks ~latency:0
|> Temporal.temporal_join
     ~key_main:(fun t -> t.bus_id)
     ~key_upd:(fun a -> a.a_bus)
     ~valid_from:(fun a -> a.a_ts)
     ~merge:(fun t a -> match a with Some a -> { t with depot=a.a_depot } | None -> t)
     ~updates:assignment_updates
```

В примере поток апдейтов специально подан «неправильно»: апдейт
`B1→north` с `valid_from=0` приходит **после** `B1→south` с
`valid_from=100`. То есть нужная для показания `t=50` версия (north)
прибывает позже конкурирующей. Несмотря на это:

```
апдейт 'B1→north@0' пришёл ПОСЛЕ 'B1→south@100' (опоздал)
  B1 @50s  → депо north  (на момент события)
  B1 @150s → депо south  (на момент события)
=== temporal даёт верное депо НА МОМЕНТ события даже при опоздавшем
    апдейте: true ===
```

### 10.1. Как это работает

Два механизма:

1. **Версионированная таблица.** Вместо «последнего значения» по ключу
   хранится **история** `(valid_from, value)`. `put_version` вставляет с
   сохранением сортировки, поэтому опоздавший апдейт со старым
   `valid_from` встаёт на своё место. `as_of key ts` находит версию,
   действовавшую на `ts` (наибольший `valid_from <= ts`).

2. **Удержание по watermark апдейтов.** Показание с временем `T` не
   обогащается сразу — оно **буферизуется**, пока watermark потока
   апдейтов не достигнет `T`. Только тогда гарантировано, что все апдейты
   с `valid_from <= T` уже прибыли (включая опоздавшие). После этого
   `as_of` даёт правильную версию, и показание эмитится.

Именно удержание превращает «гонку прихода» в детерминированный результат
по event-time. Без него показание `t=50`, обработанное до прихода
опоздавшего `north@0`, ошибочно получило бы `south` (или `None`).

### 10.2. Цена и границы

- **Буферизация = задержка и память.** Показание ждёт, пока watermark
  апдейтов его догонит. Если поток апдейтов «молчит», watermark не растёт
  (для этого есть idle-watermarks — отдельный механизм), и показания
  копятся. Это фундаментальный компромисс temporal join: корректность по
  event-time стоит задержки и буфера.
- **Watermark апдейтов должен быть честным.** Гарантия держится на
  обещании watermark «апдейтов раньше этого времени больше не будет».
  Если источник апдейтов нарушит это (пришлёт апдейт с `valid_from`
  меньше уже выданного watermark) — гарантия нарушится. Это контракт
  watermark, общий для всей event-time модели.

> Это и есть разница, которую обещает temporal join во Flink
> (`FOR SYSTEM_TIME AS OF`): результат привязан к версии справочника на
> event-time строки, а не к «текущей» версии. ex05 показывает обе
> семантики рядом ([F] snapshot vs [G] temporal), чтобы разница была
> наглядной.

## Что забрать из примера

1. **Беспорядок — норма, и движок к нему устойчив.** out-of-order,
   опоздавшие и дубли не искажают результат, потому что окна работают по
   event-time. Пример это **доказывает** сравнением с упорядоченным
   прогоном, а не декларирует.
2. **Сбои изолируются, а не роняют поток.** `safe_map` превращает
   исключение на одном событии в пропуск этого события.
3. **Состояние переживает краш.** Exactly-once checkpoint + recovery дают
   результат, идентичный прогону без сбоя (в рамках single-node).
4. **Композиция важнее магии.** Весь пайплайн — это `|>`-труба маленьких
   операторов и комбинируемых агрегаторов. Никакого скрытого
   фреймворк-волшебства; всё, что происходит, видно в типах.
5. **Границы заявлены честно.** Дубли не дедуплицируются сами (для этого
   `dedup`); EO — single-node; `allowed_lateness` — компромисс между
   полнотой захвата опоздавших и удержанием окон в памяти.

### Про `allowed_lateness` как настройку

Корректность в [A] держится на том, что `allowed_lateness` (30с) покрывает
фактический разброс опозданий (~20с). Это **компромисс**: больший допуск
ловит больше опоздавших, но дольше держит окна в памяти и порождает больше
retract'ов вниз по потоку. Событие, опоздавшее сверх `allowed_lateness`,
будет отброшено — и тогда «out-of-order == in-order» уже не выполнится для
него. Пример показывает корректный случай; конкретное значение реальное
приложение подбирает под измеренный профиль опозданий своих источников.

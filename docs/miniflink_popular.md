# miniFlink — Потоки данных: от датчика до алерта

*Как работают системы обработки данных в реальном времени — объясняем просто*

---

## Глава 1. Что такое поток данных

Представь что у тебя тысяча грузовиков и каждый каждые 100 миллисекунд
отправляет сообщение: скорость, топливо, координаты. Это **поток данных** —
бесконечная река сообщений которая никогда не заканчивается.

Традиционный подход: копить данные, потом анализировать. Но если грузовик
едет 200 км/ч прямо сейчас — ждать до ночи не получится.

**Потоковая обработка** — это анализ данных по мере их поступления,
без накопления.

---

## Глава 2. Поток как функция

В нашей системе поток — это просто функция:

```
следующее_событие() → значение или «ничего»
```

Вызываешь функцию — получаешь следующее событие. Вызываешь снова — следующее.
Когда поток закончился — получаешь «ничего».

Это называется **pull-модель**: ты тянешь данные когда готов их обработать,
а не данные толкают тебя.

---

## Глава 3. Event Time и Processing Time

У каждого события есть два времени:

| Время | Что это | Пример |
|-------|---------|--------|
| **Event Time** | Когда событие произошло на устройстве | 14:23:05.100 — датчик truck_A |
| **Processing Time** | Когда сервер получил сообщение | 14:23:05.350 — задержка сети |

Мы всегда работаем с **Event Time**. Иначе получим неправильные результаты:
если сеть лагает на 5 секунд, событие с «прошлым» временем придёт в «будущем»
окне и испортит статистику.

---

## Глава 4. Watermarks — граница прошлого

Как узнать что все события за промежуток [0..30 сек) уже получены и
можно считать статистику?

**Watermark** — это специальный маркер в потоке который говорит:
«все события с временем меньше X уже точно пришли».

```
[Data t=5s] [Data t=12s] [Data t=8s] [Watermark t=27s] → закрываем окно [0..30s)
```

Watermark никогда не идёт назад — это гарантировано типом системы.

---

## Глава 5. Окна — группировка по времени

**Tumbling window** (прыгающее) — неперекрывающиеся интервалы:

```
[0..30s) [30..60s) [60..90s) ...
```

**Sliding window** (скользящее) — перекрывающиеся:

```
[0..60s) [30..90s) [60..120s) ...  ← размер 60s, шаг 30s
```

Когда watermark закрывает окно — все накопленные события передаются
агрегирующей функции.

---

## Глава 6. KEYED — ключ группировки

Статистику нужно считать отдельно по каждому грузовику.
Для этого есть концепция **ключа группировки**.

В нашей системе ключ описывается **один раз в типе**:

```ocaml
module Telemetry = Keyed.Make(struct
  type t = telemetry
  let key t = t.device_id  (* ← ключ для всего что связано с Telemetry *)
end)
```

После этого все операторы — `window`, `enrich`, `dedup` —
знают ключ автоматически. Не нужно писать `~key:(fun t -> t.device_id)` везде.

## Глава 7. Декларативный pipeline

Вот весь pipeline мониторинга грузовиков — 10 строк:

```ocaml
let pipeline source =
  source
  |> Event.with_watermarks   ~latency:(seconds 3)   (* добавить watermarks *)
  |> Pipe.enrich (module Telemetry)                  (* обогатить из справочника *)
       ~from:devices
       ~merge:(fun t dev -> { t with device = dev })
  |> Pipe.window (module Telemetry)                  (* разбить на 30с окна *)
       (Pipe.tumbling (seconds 30))
  |> Pipe.aggregate Rules.compute                    (* считать статистику *)
  |> Pipe.flat_map (Rules.check Rules.fleet)         (* проверить правила *)
  |> Pipe.dedup (module Alert)                       (* убрать дубли *)
       ~rule:(fun a -> a.rule)
       ~cooldown:(minutes 5)
```

Это **декларативный** стиль: описываем *что* делать, а не *как*.
Нет циклов, нет ручного управления состоянием, нет `if (key != null)`.

## Глава 8. Обогащение данных

Датчик присылает только `device_id`. Но нам нужно знать: чья это машина,
какой лимит скорости, в каком регионе.

**Enrich** — оператор который добавляет данные из справочной таблицы:

```
Телеметрия: { device_id="truck_A", speed=95, fuel=30 }
Справочник: { device_id="truck_A", owner="ООО Яблоки", max_speed=90 }
     ↓
Результат: { ..., device = Some { owner="ООО Яблоки", max_speed=90 } }
```

Если устройство не найдено в справочнике — `device = None`.
Система не падает, просто продолжает работу без обогащения.

## Глава 9. Таблицы и Join

**Static table** — загружается один раз при старте. Справочник устройств.

**Snapshot table** — обновляется из потока. Последнее известное состояние.

**Interval join** — соединить два потока: событие из потока A соединяется
с событием из потока B если их ключи совпадают и разница во времени
не больше заданного окна.

---

## Глава 10. Exactly-Once — ровно один раз

Что если сервер упал в середине обработки?

**At-most-once**: при сбое часть сообщений теряется. Просто, но неточно.  
**At-least-once**: при сбое сообщения обрабатываются снова — дубли.  
**Exactly-once**: каждое сообщение обрабатывается ровно один раз.

Exactly-once реализуется через **checkpoint**:
1. Периодически сохраняем `(номер_эпохи, позиция_в_источнике, состояние)`
2. При сбое: восстанавливаем состояние, перематываем источник на сохранённую позицию
3. Продолжаем с того же места

## Глава 11. Ретракции — поздние данные

Окно [0..30s) закрылось. Выдан результат: средняя скорость truck_A = 70 км/ч.  
Через секунду приходит опоздавшее событие: t=8s, speed=130 км/ч.

Без ретракций — результат неверен навсегда.  
С ретракциями — система выдаёт:

```
RETRACT { truck_A, avg=70 }    ← отменяем старый
DATA    { truck_A, avg=82 }    ← выдаём новый
```

Downstream видит пару и делает upsert.

## Глава 12. Ортогональность — заменяем части независимо

Каждый компонент системы заменяется не трогая остальные:

| Что меняем | Варианты |
|-----------|---------|
| Формат данных | JSON → Protobuf: одна строка в `codec` |
| Хранилище состояния | Память → RocksDB: меняем `state_backend` |
| Параллелизм | OCaml 4 Thread → OCaml 5 Domain: `Makefile` решает |
| Режим работы | Тесты → Production: одна строка `Runtime.run` |

## Глава 13. Dead Letter Queue — карантин для плохих данных

Датчик иногда присылает сломанный JSON. Что делать?

**Без DLQ**: исключение → падение всего pipeline.  
**С DLQ**: сломанное сообщение → очередь плохих данных → pipeline продолжает.

```
Kafka → safe_decode → OK: дальше в pipeline
                    → Error: DLQ { topic, payload, error, timestamp }
```

Инженер потом разбирается с плохими сообщениями отдельно.

---

## Глава 14. Graceful Shutdown — правильное завершение

При обновлении системы нельзя просто убить процесс — потеряем данные в буфере.

**SIGTERM → последовательность:**
1. `running := false` — source перестаёт читать новые события
2. Pipeline дочитывает всё что уже в буфере
3. Sink сбрасывает накопленное (flush)
4. Checkpoint сохраняется
5. Процесс завершается

Никаких потерь.

## Глава 15. Метрики — видим что происходит

В production нужно знать: сколько событий обрабатывается, какая задержка,
есть ли проблемы.

Система экспортирует метрики в **Prometheus** формате:

```
# TYPE miniflink_events_in counter
miniflink_events_in{pipeline="fleet"} 1234567

# TYPE miniflink_window_close_us histogram
miniflink_window_close_us_bucket{le="1000"} 98521
miniflink_window_close_us_bucket{le="10000"} 99987
miniflink_window_close_us_count 100000
```

Prometheus забирает эти данные раз в 15 секунд, Grafana строит графики.

## Глава 16. Тесты — уверенность что всё работает

**22 unit теста** — каждое правило проверяется с известным ответом:
- Водяной знак никогда не идёт назад
- 3 события в окне → count = 3
- Dedup подавляет дубли в течение 5 минут

**1400 property тестов** (QCheck) — система сама придумывает случайные данные:
- Сумма событий по окнам = общее число событий (для любых данных)
- Dedup идемпотентен (второй прогон ничего не меняет)
- `speed > 1.3 × limit` тогда и только тогда выдаётся Critical алерт

## Словарь

| Термин | Значение |
|--------|---------|
| **Event Time** | Время когда событие произошло на устройстве |
| **Watermark** | Граница: все события до этого момента уже получены |
| **Tumbling window** | Неперекрывающиеся временные окна |
| **KEYED** | Тип который знает свой ключ группировки |
| **Enrich** | Обогащение события данными из справочника |
| **Retract** | Отмена предыдущего результата при поздних данных |
| **Exactly-once** | Каждое сообщение обработано ровно один раз |
| **DLQ** | Dead Letter Queue — карантин для плохих сообщений |
| **Checkpoint** | Сохранённое состояние для восстановления после сбоя |
| **Prometheus** | Система сбора метрик |

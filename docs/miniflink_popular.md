# miniFlink — Потоки данных: от датчика до алерта

*Как работают системы обработки данных в реальном времени — объясняем просто*

---

## Глава 1. Что такое поток данных

Представь что у тебя тысяча грузовиков и каждый каждые 100 миллисекунд
отправляет сообщение: скорость, топливо, координаты. Это **поток данных** —
бесконечная река сообщений которая никогда не заканчивается.

Традиционный подход: копить данные, потом анализировать. Но если грузовик
едет 200 км/ч прямо сейчас — ждать до ночи не получится.

**Потоковая обработка** — это анализ данных по мере их поступления,
без накопления.

---

## Глава 2. Поток как функция

В нашей системе поток — это просто функция:

```
следующее_событие() → значение или «ничего»
```

Вызываешь функцию — получаешь следующее событие. Вызываешь снова — следующее.
Когда поток закончился — получаешь «ничего».

Это называется **pull-модель**: ты тянешь данные когда готов их обработать,
а не данные толкают тебя.

---

## Глава 3. Event Time и Processing Time

У каждого события есть два времени:

| Время | Что это | Пример |
|-------|---------|--------|
| **Event Time** | Когда событие произошло на устройстве | 14:23:05.100 — датчик truck_A |
| **Processing Time** | Когда сервер получил сообщение | 14:23:05.350 — задержка сети |

Мы всегда работаем с **Event Time**. Иначе получим неправильные результаты:
если сеть лагает на 5 секунд, событие с «прошлым» временем придёт в «будущем»
окне и испортит статистику.

---

## Глава 4. Watermarks — граница прошлого

Как узнать что все события за промежуток [0..30 сек) уже получены и
можно считать статистику?

**Watermark** — это специальный маркер в потоке который говорит:
«все события с временем меньше X уже точно пришли».

```
[Data t=5s] [Data t=12s] [Data t=8s] [Watermark t=27s] → закрываем окно [0..30s)
```

Watermark никогда не идёт назад — это гарантировано типом системы.

---

## Глава 5. Окна — группировка событий

**Tumbling window** (прыгающее) — неперекрывающиеся интервалы:

```
[0..30s) [30..60s) [60..90s) ...
```

**Sliding window** (скользящее) — перекрывающиеся:

```
[0..60s) [30..90s) [60..120s) ...  ← размер 60s, шаг 30s
```

Когда watermark закрывает окно — все накопленные события передаются
агрегирующей функции.

Кроме окон по времени есть ещё три типа. **Count window** — окно
закрывается каждые N событий, а не по времени (watermark не нужен:
ровно отсчитали сколько надо — выдали). **Session window**
(сессионное) — границы плавающие: окно растёт пока события идут часто,
и закрывается после паузы. А если событие попадает в разрыв между двумя
сессиями — они **сливаются** в одну. Это как «период активности»: человек
под землёй передаёт сигналы — пока передаёт, сессия идёт; замолчал
надолго — сессия закрыта. **Global window** — одно окно на ключ, которое
закрывается не по расписанию, а по явному **триггеру**: можно сказать
«фаерь каждые N событий» или «фаерь сразу как пришло тревожное значение»
(ранняя реакция, не дожидаясь конца окна).

У триггера два режима эмиссии. **FireAndPurge** — выдать накопленное и
очистить буфер (окна не пересекаются, каждое событие учтено ровно раз).
**Fire** — выдать, но буфер сохранить (накопительно: каждая эмиссия —
это «всё что было до сих пор»). При накопительном режиме на конце потока
остаток выдаётся только если в нём есть события, которые ещё не выходили
— поэтому если последним действием был Fire и новых данных не пришло,
лишней копии не будет. Если же после Fire события накопились — на конце
выйдет обновлённое, большее состояние (это не дубль, а догнавшие данные).

## Глава 5.5. Агрегация окна: список или аккумулятор

Окно собрало события — что с ними делать? Простой путь: окно отдаёт
список, ты его сворачиваешь (`aggregate`). Но хранить весь список —
дорого: на окне в миллион событий это миллион значений в памяти.

Есть инкрементальный путь: вместо списка окно держит **аккумулятор** и
обновляет его на каждом событии сразу (`window_fold`). Считаешь сумму —
храни одно число, а не миллион. Память O(1) на окно вместо O(n).

И поверх этого — **комбинируемые агрегаторы** (`Agg`). Вместо того чтобы
каждый раз писать свёртку вручную, берёшь готовый: `Agg.mean`, `Agg.max_by`,
`Agg.count`, `Agg.arg_max` (вернёт сам элемент с максимумом, не число) и
другие. Самое полезное — их можно **складывать**: посчитать среднее И
максимум за один проход по окну:

```
Agg.(both (mean temp) (max_by temp))
```

Или через let-синтаксис, когда агрегатов много:

```
Agg.(
  let+ n   = count
  and+ avg = mean temp
  and+ hi  = max_by temp in
  (n, avg, hi))
```

Это считается одним проходом — не три раза по окну. `Pipe.window_agg`
применяет такой агрегат к окнам, инкрементально. Маленькие
комбинируемые кусочки вместо ручных циклов — так в OCaml выходит и
выразительно, и эффективно.

## Глава 6. KEYED — ключ группировки

Статистику нужно считать отдельно по каждому грузовику.
Для этого есть концепция **ключа группировки**.

В нашей системе ключ описывается **один раз в типе**:

```ocaml
module Telemetry = Keyed.Make(struct
  type t = telemetry
  let key t = t.device_id  (* ← ключ для всего что связано с Telemetry *)
end)
```

После этого все операторы — `window`, `enrich`, `dedup` —
знают ключ автоматически. Не нужно писать `~key:(fun t -> t.device_id)` везде.

## Глава 7. Декларативный pipeline

Вот весь pipeline мониторинга грузовиков — 10 строк:

```ocaml
let pipeline source =
  source
  |> Event.with_watermarks   ~latency:(seconds 3)   (* добавить watermarks *)
  |> Pipe.enrich (module Telemetry)                  (* обогатить из справочника *)
       ~from:devices
       ~merge:(fun t dev -> { t with device = dev })
  |> Pipe.window (module Telemetry)                  (* разбить на 30с окна *)
       (Pipe.tumbling (seconds 30))
  |> Pipe.aggregate Rules.compute                    (* считать статистику *)
  |> Pipe.flat_map (Rules.check Rules.fleet)         (* проверить правила *)
  |> Pipe.dedup (module Alert)                       (* убрать дубли *)
       ~rule:(fun a -> a.rule)
       ~cooldown:(minutes 5)
```

Это **декларативный** стиль: описываем *что* делать, а не *как*.
Нет циклов, нет ручного управления состоянием, нет `if (key != null)`.

## Глава 8. Обогащение данных

Датчик присылает только `device_id`. Но нам нужно знать: чья это машина,
какой лимит скорости, в каком регионе.

**Enrich** — оператор который добавляет данные из справочной таблицы:

```
Телеметрия: { device_id="truck_A", speed=95, fuel=30 }
Справочник: { device_id="truck_A", owner="ООО Яблоки", max_speed=90 }
     ↓
Результат: { ..., device = Some { owner="ООО Яблоки", max_speed=90 } }
```

Если устройство не найдено в справочнике — `device = None`.
Система не падает, просто продолжает работу без обогащения.

---

## Глава 9. Таблицы и Join

**Static table** — загружается один раз при старте. Справочник устройств.

**Snapshot table** — обновляется из потока. Последнее известное состояние.

**Interval join** — соединить два потока: событие из потока A соединяется
с событием из потока B если их ключи совпадают и разница во времени
не больше заданного окна.

---

## Глава 9.5. Несколько потоков: union и живые таблицы

Реальная система редко имеет один источник. В шахте это поток
позиционирования людей, поток газовых датчиков, поток конфигурации.
Их нужно соединять.

**Union — слияние потоков по времени.** `union` берёт два потока и
сливает в один, упорядочивая по event-time. Важная тонкость: это не
«сначала весь первый, потом второй», а honest merge — на каждом шаге
берётся событие с меньшим временем. Поэтому объединённый поток остаётся
упорядоченным, и окна ниже по течению работают правильно.

С watermarks есть тонкость: watermark объединённого потока — это
**минимум** watermarks обоих входов. Логика простая: нельзя сказать «время
T прошло», пока хотя бы один вход это не подтвердил. Если один поток
«убежал» вперёд, а второй отстаёт — общая граница идёт по отстающему.
Иначе бы мы закрыли окно, в которое из медленного потока ещё прилетят
события.

**Живые таблицы из потока.** Бывает что один поток должен обновлять
справочник, из которого обогащается другой. Пример: поток конфигурации
датчиков задаёт пороги, а поток показаний обогащается этими порогами.
`update_table` пропускает поток через себя, попутно обновляя таблицу.
Другой поток через `enrich` из этой таблицы читает уже актуальные
значения — таблица «живая», меняется по ходу.

```
config ──update_table──> [таблица порогов]
                                │
data ───────enrich──────────────┘──> обогащённые данные
```

**Temporal join — «как было на момент события».** У живой таблицы есть
подвох. Представь: автобус B1 был приписан к северному депо, а в полдень
его перевели в южное. Приходит показание, снятое утром — к какому депо его
отнести? `enrich` из живой таблицы ответит «южное», потому что таблица
показывает *текущее* состояние. Но это неправильно: утром автобус был на
севере. Правильный ответ — депо, актуальное **на момент самого показания**.

Это и есть temporal join: справочник хранит не последнее значение, а
**историю версий** («с утра — север, с полудня — юг»), и каждое показание
обогащается версией, действовавшей в его event-time.

Самое коварное — когда апдейт справочника **опаздывает**. Сообщение «B1 с
утра на севере» по дороге застряло и пришло позже, чем «B1 с полудня на
юге». Наивная обработка успела бы отдать показанию неверное депо. miniFlink
решает это так же, как с опоздавшими данными вообще — через watermark:
показание **придерживается** в буфере, пока watermark потока апдейтов не
догонит его время. Только тогда мы уверены, что все апдейты (включая
опоздавшие) на этот момент прибыли — и отдаём показанию правильную версию.
Результат получается один и тот же независимо от того, в каком порядке всё
пришло. Платим за это задержкой и памятью на буфер — честная цена за
корректность.

## Глава 10. Exactly-Once — ровно один раз

Что если сервер упал в середине обработки?

**At-most-once**: при сбое часть сообщений теряется. Просто, но неточно.  
**At-least-once**: при сбое сообщения обрабатываются снова — дубли.  
**Exactly-once**: каждое сообщение обрабатывается ровно один раз.

Exactly-once реализуется через **checkpoint**:
1. Периодически сохраняем `(номер_эпохи, позиция_в_источнике, состояние)`
2. При сбое: восстанавливаем состояние, перематываем источник на сохранённую позицию
3. Продолжаем с того же места

**А если воркеров несколько?** Тогда нужен согласованный снимок всех
сразу — алгоритм Chandy-Lamport. Координатор отправляет специальный
маркер-«барьер» во все каналы. Каждый воркер, получив барьер,
сохраняет свой кусочек состояния и сообщает координатору «готов».
Когда готовы все — checkpoint фиксируется атомарно. Получается
согласованный срез: всё до барьера учтено, всё после — нет. Поскольку
каждый ключ всегда идёт к одному воркеру, состояние не задваивается.

**Коварная ловушка.** Казалось бы, позицию в источнике взять легко:
сколько прочитал — то и запомнил. Но тот кто читает источник, бежит
*впереди* воркеров: он уже прочитал 2000 событий, а воркеры обработали
только 1900 — остальные ещё летят по очередям. Если запомнить «2000»,
а в состоянии лежит 1900, то после сбоя мы перемотаемся на 2000 и
**потеряем 100 событий** — их нет ни в состоянии, ни в перечитывании.
Тихая потеря данных, которую не видно пока объёмы маленькие.

Решение: позицию считает не читатель, а сами воркеры — каждый помнит
сколько обработал, и записывает это число в тот же момент что и снимок
состояния. Тогда позиция и состояние всегда совпадают. Этот баг прошёл
обычные тесты и попался только на проверке «позиция == состояние» — и
это урок: exactly-once проверяют не вопросом «работает ли», а вопросом
«согласованы ли инварианты».

**А что на выходе?** После сбоя мы переобработаем последние события —
и они пройдут через получателя (sink) второй раз. Состояние-то мы
восстановили, а вот в базу или в Kafka результат запишется дважды.
Два решения: либо писать **идемпотентно** (по детерминированному ключу
с перезаписью — повтор перезапишет тем же, безвредно), либо настоящий
**двухфазный коммит** — результат сначала «невидим», и становится виден
только когда checkpoint зафиксирован. Идемпотентность проще и работает
почти везде; 2PC мощнее, но годится только для систем умеющих
транзакции (Kafka, БД) — для HTTP-запроса или SMS его не сделать,
там только идемпотентность.

> Подробный технический разбор — почему exactly-once трудный, как
> ломается и как сделано — в [docs/exactly_once.md](exactly_once.md).

## Глава 11. Ретракции — поздние данные

Окно [0..30s) закрылось. Выдан результат: средняя скорость truck_A = 70 км/ч.  
Через секунду приходит опоздавшее событие: t=8s, speed=130 км/ч.

Без ретракций — результат неверен навсегда.  
С ретракциями — система выдаёт:

```
RETRACT { truck_A, avg=70 }    ← отменяем старый
DATA    { truck_A, avg=82 }    ← выдаём новый
```

Downstream видит пару и делает upsert.

Каждый компонент системы заменяется не трогая остальные:

|-----------|---------|
| Формат данных | JSON → Protobuf: одна строка в `codec` |

| Режим работы | Тесты → Production: одна строка `Runtime.run` |

## Глава 13. Dead Letter Queue — карантин для плохих данных

Датчик иногда присылает сломанный JSON. Что делать?

**Без DLQ**: исключение → падение всего pipeline.  
**С DLQ**: сломанное сообщение → очередь плохих данных → pipeline продолжает.

```
Kafka → safe_decode → OK: дальше в pipeline
                    → Error: DLQ { topic, payload, error, timestamp }
```

Инженер потом разбирается с плохими сообщениями отдельно.

То же касается не только декодирования. Любая твоя функция в pipeline —
валидация, преобразование — может споткнуться на одном кривом событии.
Обычный `map` пробросил бы исключение и уронил весь поток из-за одного
показания. `safe_map ~on_error` ловит исключение на конкретном событии,
вызывает твой обработчик (записать в лог, инкрементить счётчик) и
**пропускает** это событие — поток живёт дальше. Один сбойный датчик не
останавливает обработку всего флота.

## Глава 14. Graceful Shutdown — правильное завершение

При обновлении системы нельзя просто убить процесс — потеряем данные в буфере.

**SIGTERM → последовательность:**
1. `running := false` — source перестаёт читать новые события
2. Pipeline дочитывает всё что уже в буфере
3. Sink сбрасывает накопленное (flush)
4. Checkpoint сохраняется
5. Процесс завершается

Никаких потерь.

## Глава 15. Метрики — видим что происходит

В production нужно знать: сколько событий обрабатывается, какая задержка,
есть ли проблемы.

Система экспортирует метрики в **Prometheus** формате:

```
# TYPE miniflink_events_in counter
miniflink_events_in{pipeline="fleet"} 1234567

# TYPE miniflink_window_close_us histogram
miniflink_window_close_us_bucket{le="1000"} 98521
miniflink_window_close_us_bucket{le="10000"} 99987
miniflink_window_close_us_count 100000
```

Prometheus забирает эти данные раз в 15 секунд, Grafana строит графики.

Самая важная метрика для стриминга — **watermark lag**: насколько
watermark отстаёт от самого свежего события. Растёт lag — значит
система не успевает, окна закрываются с задержкой.

## Глава 15.5. Где хранится состояние

Окна, счётчики дедупликации, агрегаты — всё это **состояние**. Где
оно живёт?

- **В памяти** — быстро, но теряется при перезапуске.
- **В RocksDB** — встроенная база ключ-значение от Facebook. Состояние
  переживает перезапуск процесса: остановили, запустили снова — данные
  на месте.

RocksDB написана на C++, поэтому miniFlink обращается к ней через
**FFI** (foreign function interface) — мост между OCaml и C. Тонкое
место: память. OCaml-сборщик мусора может двигать объекты, поэтому
байты копируются через границу немедленно — никаких «висящих»
указателей. Сделаешь неаккуратно — получишь segfault; сделаешь
правильно — получишь надёжное хранилище.

## Глава 16. Тесты — уверенность что всё работает

**Unit-тесты** — каждое правило проверяется с известным ответом:
водяной знак не идёт назад, 3 события в окне → count = 3, dedup
подавляет дубли 5 минут.

**Property-тесты** (QCheck) — система сама придумывает случайные данные
и проверяет инварианты: сумма событий по окнам = общему числу,
dedup идемпотентен, `speed > 1.3 × limit` ⟺ Critical-алерт.

Но для потоковой системы этого мало. Главные тесты — про то что
ломается именно в стриминге:

- **Детерминизм воспроизведения**: один и тот же вход дважды → байт-в-байт
  одинаковый выход. Это фундамент exactly-once.
- **Параллель = последовательность**: 4 воркера дают тот же *набор*
  алертов что один поток. Порядок между ключами не важен — сравниваем
  множества. Доказывает что шардинг ничего не теряет и не дублирует.
- **Фаззинг watermark**: случайно перемешанные по времени потоки —
  инварианты окон держатся.
- **Восстановление**: упали, восстановились из checkpoint — состояние
  на месте.
- **Soak-тест**: миллионы событий, проверка что память не растёт
  (eviction в dedup и окнах работает).

Всего 27 наборов тестов, запускаются одной командой `dune test`.

## Словарь

| Термин | Значение |
|--------|---------|
| **Event Time** | Время когда событие произошло на устройстве |
| **Watermark** | Граница: все события до этого момента уже получены |
| **Tumbling window** | Неперекрывающиеся временные окна |
| **KEYED** | Тип который знает свой ключ группировки |
| **Enrich** | Обогащение события данными из справочника |
| **Retract** | Отмена предыдущего результата при поздних данных |
| **Exactly-once** | Каждое сообщение обработано ровно один раз |
| **DLQ** | Dead Letter Queue — карантин для плохих сообщений |
| **Checkpoint** | Сохранённое состояние для восстановления после сбоя |
| **Barrier** | Маркер для согласованного снимка нескольких воркеров (Chandy-Lamport) |
| **Watermark lag** | Насколько watermark отстаёт от самого свежего события |
| **RocksDB** | Встроенная БД ключ-значение для персистентного состояния |
| **FFI** | Мост между OCaml и кодом на C (для RocksDB) |
| **Prometheus** | Система сбора метрик |

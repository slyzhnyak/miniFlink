# Ревью проекта: декларативность DSL, ошибки, unhappy paths (2026-07)

Внутреннее ревью с тремя фокусами: (1) выразительность и декларативность
полученного языка — главная цель проекта; (2) поведение на ошибках;
(3) unhappy paths. Материал: ex07 (флагманский пример, 1671 строка),
публичная поверхность API (pipe.mli, agg.mli, trigger.mli, item.mli,
mf_event.mli), реализация операторов. Все утверждения проверены по коду,
строки указаны.

## Вердикт

Цель «декларативный язык описания потоковой обработки» достигнута
**наполовину**, и ex07 — честная демонстрация обеих половин.

Хорошая половина: линейные конвейеры с окнами и агрегатами. Оконная
часть `median_rssi` читается как спецификация, а не как программа:

```ocaml
source
|> Pipe.dedup (module ByLamp) ~rule ~cooldown:(seconds 120)
|> Pipe.flat_map explode_readings
|> Pipe.event_time ~lateness:(seconds 1)
|> Pipe.window_agg_keyed ~by:lamp (Pipe.sliding (seconds 60) (seconds 5))
     Agg.(group_by ~key:beacon ~inner:(median rssi)
          |> map (top_k 2))
```

Это уровень Flink SQL по читаемости. Agg-комбинаторы (`group_by`,
`median`, `top_k_by`, композиция через `|>` и `map`) — сильнейшая часть
DSL.

Плохая половина: как только задача выходит за «один поток → окно →
агрегат», пользователь **падает с обрыва DSL в ручную сантехнику**.
В ex07 из 605 строк pipelines.ml собственно декларативных — около 30.
Остальное — ровно тот императивный код (мутабельные записи, Hashtbl
состояний, ручные циклы по конструкторам событий, ручное управление
таймерами), который библиотека обязана прятать. Причём это не неумение
автора примера — это **дыры в поверхности DSL**, каждая из которых ниже
названа поимённо.

## Часть 1. Разбор ex07 по трём пайплайнам

### 1.1 median_rssi — оценка 4/5, портит хвост

Конвейер декларативен до последнего шага. А последний шаг — 18-строчный
анонимный ручной переписчик потока (pipelines.ml:143-160):

```ocaml
|> (fun stream ->
     let rec out () =
       match stream () with
       | None -> None
       | Some (Mf_event.Data ((lamp, top2), wend)) ->
         Some (Mf_event.Data (build_loc lamp top2 wend, wend))
       | Some (Mf_event.Retract ...) -> ...
       | Some (Mf_event.Update ...) -> ...
       | Some (Mf_event.Watermark wm) -> ...
     in out)
```

Зачем он существует: `build_loc` нужен **ts события** (`wend` — конец
окна), а `Pipe.map` даёт callback'у только значение. `Mf_event.map_value`
корректно обрабатывает все четыре конструктора — не хватает одной
функции с сигнатурой `map_ts : ('a -> Time.t -> 'b) -> ...`. Отсутствие
однострочника заставило написать вручную то, что библиотека уже умеет.

**Разрыв G-1: нет `Pipe.map_ts`** (map с доступом к timestamp).

### 1.2 connectivity_alerts — оценка 2/5: библиотека не использована библиотекой

~200 строк (pipelines.ml:163-372): три слоя ручной машинерии
(`Last_seen` — мутабельная запись фактов; `Self_timer` — ручной
перенос одного таймера; `Fsm` — три функции переходов), клей `per_lamp`
с четырьмя mutable-полями и `check_and_emit` на 30 строк.

Главная претензия: **в библиотеке есть Trigger** (lib/trigger.ml,
477 строк) — с гистерезисом, debounce, sticky-состояниями, таймерами.
Voltage-FSM примера (Ok / Suspect / Low с debounce на вход и
гистерезисом на выход) — это *дословно* то, что делает
`Trigger.create ~condition ~debounce ~hysteresis`. И флагманский пример
его не использует. Почему — видно из ограничений Trigger:

1. **Триггерится только на пришедшие значения.** Условия ex07 — на
   *отсутствие* (нет пакетов 60с, нет движения 300с). Для отсутствия
   есть `Item.silence_age`, и связка `silence_age |> Trigger.of_stream`
   в принципе выражает «тишина дольше N» — но в примере она не
   применена, и непонятно, применима ли: нужны 4 разных silence на
   один ключ.
2. **Нет подавления между автоматами.** Motion и voltage должны
   молчать при `No_packets` (мы не знаем, а не «плохо»). Trigger — один
   независимый автомат на спеку; `combine` объединяет потоки алертов,
   но не даёт одному автомату видеть состояние другого.
3. **`Self_timer` — boilerplate, нужный каждому.** «Один логический
   таймер на ключ с переносом цели» — паттерн, который перепишет каждый
   пользователь `process_keyed` с таймаутами. Ему место в библиотеке.

**Разрыв G-2: Trigger не композируется** — нет gate/suppress_when по
состоянию другого автомата, нет условий на тишину как first-class.
**Разрыв G-3: нет helper'а single-timer-per-key.**

### 1.3 gas_alerts — оценка 1/5: полный сход с DSL, признанный кодом

Smoking gun — комментарий в самом примере (pipelines.ml:525):

> «process_keyed не подходит здесь: его ctx.emit ожидает только
> значение (не Mf_event), и мы не можем эмитить retract'ы. Делаем
> руками — это нормально для нестандартной retract-семантики.»

«Делаем руками — это нормально» — не нормально, когда цель проекта —
декларативность. Retract-семантика в потоковой библиотеке с
Update/Retract-моделью — не «нестандартная», это её ядро. Что пользователь
делает руками (pipelines.ml:513-605):

- объявляет union-тип `gas_input` с тремя конструкторами и пишет три
  `Pipe.map`-обёртки, чтобы слить три разнотипных потока;
- пишет `Keyed.Make` по этому union-типу с ручным диспатчем ключа;
- держит собственный `Hashtbl<lamp, gas_state>` — то есть сам реализует
  keyed state, который у библиотеки уже есть в `process_keyed`;
- держит собственный `Queue` исходящих событий;
- пишет `let rec next ()` с ручной обработкой всех четырёх конструкторов
  Mf_event, включая ручной проброс Watermark.

Это 90 строк каркаса, идентичного внутренностям `process_keyed`, — ради
одной недостающей возможности: **эмитить `Retract`/`Update` из
per-key логики**. `ctx.emit : 'out -> unit` умеет только Data.

Вторая причина схода: **нет со-обработки разнотипных потоков на общем
ключе** (аналог Flink `connect` + CoProcessFunction). Паттерн «driver
stream + side inputs, обновление side re-эмитит активные выходы» —
классика (temporal enrichment с коррекцией), и он невыразим: `enrich` —
pull-семантика (значение подтягивается при обработке события), а нужна
push (обновление позиции само переэмитило активные алерты).

**Разрыв G-4: `ctx.emit` не умеет Retract/Update** (нет `emit_event`).
**Разрыв G-5: нет co_process / connect** для N разнотипных потоков на
общем ключе — union-тип и диспатч пишутся руками каждый раз.
**Разрыв G-6: нет reactive side input** (enrich с re-emit при обновлении
справочника).

### 1.4 Сводка разрывов и их цена в ex07

| Разрыв | Строк ручного кода в ex07 | Сложность закрытия |
|---|---|---|
| G-1 map_ts | 18 | тривиально |
| G-2 Trigger composition | ~150 (могло бы быть ~40) | крупно, дизайн |
| G-3 single-timer helper | ~15 | просто |
| G-4 emit_event | ~90 (каркас gas_alerts) | средне |
| G-5 co_process | ~30 (union-тип + обёртки) | средне |
| G-6 reactive enrich | ~35 (refresh_alerts...) | средне-крупно |

Закрытие G-1+G-4+G-5 сжало бы pipelines.ml примерно с 605 до ~250 строк,
из которых декларативная доля выросла бы с ~5% до ~50%. Целевой вид
gas_alerts (эскиз):

```ocaml
let gas_alerts ~rssi ~locations ~gas () =
  Pipe.co_process3 (module ByLamp3)
    ~init:make_gas_state
    ~on_a:(fun ctx _ st loc ->        (* location: side input *)
      if update_position st loc.loc_position then
        refresh_active st |> List.iter ctx.emit_event)
    ~on_b:(fun ctx _ st pkt ->        (* raw RSSI: coarse fallback *)
      if st.position = None then set_coarse st pkt)
    ~on_c:(fun ctx _ st g ->          (* gas: driver *)
      gases_in_packet g
      |> List.concat_map (transition st)
      |> List.iter ctx.emit_event)
    (locations, rssi, gas)
```

~25 строк вместо ~200, вся доменная логика (`transition`,
`refresh_active`) — чистые функции, каркас — библиотечный.

## Часть 2. Ошибки и unhappy paths

### E-1 (worst): забытый `event_time` — тихий неверный результат

Окна закрываются только по watermark. Если пользователь не поставил
`Pipe.event_time` (или источник не эмитит watermark): на конечном потоке
все окна тихо копятся и вываливаются одним махом на end-of-stream
(window.ml:596 — «конец потока: эмитим только непустые буферы»); на
бесконечном — **копятся вечно**: утечка памяти плюс ни одного результата,
без единого warning'а. Это худший вид отказа — тихий и семантический.
Оба режима выглядят «работает», особенно первый: тесты на конечных
списках проходят, прод на бесконечном Kafka-топике молчит.

Предложение: оконные операторы считают события с момента старта и при
N событий (например 10 000) без единого Watermark — `Log.warn` один раз:
«окно не получило ни одного watermark — забыт Pipe.event_time?».
Дёшево, ловит главный footgun.

### E-2: union + замолчавший вход = остановка всего downstream

`Mf_event.union` продвигает watermark как min по входам — корректно, но
один тихий вход (сломавшийся датчик) останавливает watermark всего
графа: окна не закрываются, таймеры не срабатывают. Idle-обёртка в
библиотеке **есть** (mf_event.ml:133, `~idle_ms`), но: (а) её надо знать;
(б) в ex07 gas_alerts её нет — замолкший газовый датчик заморозил бы
таймеры connectivity, если бы они были ниже по графу. Мы сами напоролись
на этот min-эффект при написании теста C-3 (watermark не прошёл, пока
оба входа его не выдали).

Предложение: в доке union — заметный блок про min-семантику и idle;
опционально `union ~idle_timeout` как шорткат.

### E-3: несогласованная стратегия исключений (архитектурное 6.2 — подтверждаю)

`safe_map`/`safe_filter`/`safe_flat_map` ловят и шлют в DLQ;
`window*`, `process_keyed`, `trigger`, `dedup` — роняют пайплайн.
Пользовательская лямбда есть и там и там; безопасность пайплайна зависит
от того, в какой оператор попало ядовитое событие. После M-3 крах в
exactly-once корректен (эпоха откатывается, replay), но: одно ядовитое
событие → бесконечный цикл crash-recovery-crash на нём же. Для
safety-системы нужен маршрут «изолировать событие в DLQ и жить дальше»
для *всех* операторов с пользовательским кодом, не только map/filter.

Предложение: `?on_error:(Dlq | Propagate)` на process_keyed и window_fold
(остальные — по мере надобности). Default — Propagate (текущее
поведение, без сюрпризов).

### E-4: отсутствует валидация конфигурации на входах

Проверяются только window-спеки (tumbling/sliding/count — Invalid_argument,
хорошо). Не проверяются: `lateness < 0` (event_time), `cooldown < 0`
(dedup), `ttl <= 0` (keyed_join/trigger — добавили сами, но без
валидации), `workers <= 0`, `capacity <= 0`, `checkpoint_every <= 0`
(run_exactly_once). `workers = 0` упадёт, но из глубины `Hash.key`
(«число шардов должно быть > 0») — ошибка не с того входа, диагностика
хуже. `checkpoint_every = 0` — вероятно, барьер на каждое событие или
деление странностей; `lateness = -5` — молча кривые watermark'и.

Предложение: invalid_arg на входе каждого публичного конструктора с
именем параметра. Час работы, закрывает класс.

### E-5: `collect`/`to_list`/`materialize` на бесконечном потоке

Дренят до None — на бесконечном источнике зависают. В доке (pipe.mli:388+)
предупреждения нет. Это же касается самого ex07: он материализует
`location_events` в список (ex07_location.ml:37) — паттерн, который
скопируют в прод с Kafka-источником и получат вечное зависание без
диагностики.

Предложение: одна строка в доке каждого дренящего потребителя:
«⚠ бесконечный поток — вечный цикл; для бесконечных используйте sink/
iter_data с внешним стопом».

### E-6: ex07 как обучающий материал учит анти-паттернам

Следствие Части 1, но с другой стороны: пример — это то, что пользователи
копируют. Сейчас ex07 учит: «хочешь retract из keyed-логики — пиши
каркас руками», «хочешь несколько FSM — вот тебе 200 строк мутабельных
слоёв». Пока разрывы G-1..G-6 не закрыты, честнее пометить эти места в
ex07 комментарием «ограничение DSL, issue #N», чтобы читатель знал: это
не best practice, это обход.

### Что в unhappy paths хорошо (зафиксировать)

- Валидация window-спек с понятными русскими сообщениями.
- `safe_*` + DLQ с retry/backoff — продуманный happy-path для ошибок
  в map/filter.
- Поведение при крахе воркера после KI-1/M-3 — корректное и
  детерминированное (последний валидный checkpoint + replay), проверено
  property-тестами.
- `Hash.key` защищён; iter+remove вычищены; ttl-eviction добавлены.
- Trigger: key-collision между триггерами решён namespace'ами
  (test_trigger_key_collision).

## Часть 3. Приоритезированные предложения

**P1 — дёшево, закрывает видимые дыры (можно в одну сессию):**
1. `Pipe.map_ts : ('a -> Time.t -> 'b) -> ...` (G-1) — и переписать хвост
   median_rssi в ex07 на него.
2. `ctx.emit_retract : 'out -> unit` и `ctx.emit_update : old:'out ->
   'out -> unit` в process_keyed (G-4). Не ломает существующий emit.
3. Валидация входов (E-4) + doc-предупреждения collect/to_list (E-5).
4. Warning «окно без watermark» (E-1).

**P2 — средний размер, главный выигрыш выразительности:**
5. `Pipe.co_process2/3` (G-5): co-обработка разнотипных потоков на общем
   ключе, общий state, emit_event. После него переписать gas_alerts в
   ex07 — он сожмётся с ~200 до ~25-40 строк и станет демонстрацией
   силы, а не слабости.
6. `Pipe.single_timer` helper (G-3).
7. `?on_error:Dlq` для process_keyed/window_fold (E-3).

**P3 — крупный дизайн, отдельное обсуждение:**
8. Композиция триггеров (G-2): условия на тишину first-class
   (`Trigger.on_silence ~threshold`), подавление
   (`Trigger.suppress_when other_state`). Цель — connectivity_alerts
   ex07 из ~200 строк слоёв в ~40 строк деклараций четырёх автоматов.
9. Reactive enrich (G-6) — возможно, выпадет бесплатно из co_process.

**Честная оговорка о корне.** Часть ограничений растёт из pull-модели
(архитектурное 6.1 внешнего ревью): side inputs, независимые таймеры,
push-обновления в pull-мире требуют обвязок (event_time как драйвер
watermark, idle-обёртки). Pull-модель — осознанный выбор с реальными
достоинствами (простота, отсутствие callback-ада, ленивость), и менять
её не предлагается. Но надо признать: co_process и reactive enrich в
pull-модели будут реализованы поверх union + буферов — то есть тем же
кодом, что сейчас в gas_alerts, только **один раз, внутри библиотеки,
оттестированный**, а не в каждом пользовательском пайплайне заново. В
этом и есть работа DSL: не устранить сложность, а взять её на себя.

## Итог

Ядро (окна, агрегаты, event-time, exactly-once) — крепкое и после
закрытия ревью-багов надёжное. Agg — образцово декларативен. Дыра — в
**среднем слое композиции**: несколько потоков, retract из keyed-логики,
взаимодействующие автоматы, реактивное обогащение. Ровно там, где
находится реальная задача minePASS, и ровно поэтому ex07 получился
императивным. Разрывы конечны, названы (G-1..G-6), у большинства —
недорогие закрытия; P1+P2 переводят ex07 из анти-примера в витрину.

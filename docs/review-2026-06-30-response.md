# Триаж профессионального ревью (2026-06-30)

Документ фиксирует статус каждого пункта из «Professional Code Review —
Bug Analysis» (30 июня 2026): что подтверждено на актуальном коде, что
уже адресовано ранее, что является осознанным дизайном, и что фактически
неверно. Это только триаж — правок по итогам ещё не вносилось (кроме
того, что было сделано до ревью). Все проверки выполнены по исходникам
на собранном проекте, а не по памяти.

Ревью основано исключительно на исходном коде и не знало о части уже
выполненной работы (§4.1, `?on_retract` у `process_keyed`, Kafka EOS,
документ `known-issues.md`), поэтому несколько пунктов оказались уже
закрытыми или заведёнными.

## CRITICAL

### C-1 — data race на `failed[]` — ПОДТВЕРЖДЁН, ОТКРЫТ
`failed` создаётся как `Array.make workers false` (обычный bool-массив),
пишется из воркера и читается из диспетчера без синхронизации:
`variants/parallel_v5.ml:62,82` и `lib/checkpoint_parallel.ml:357,424`.
На OCaml 5 (домены, без GIL) это data race по модели памяти — читатель
может видеть устаревшее значение и слать события мёртвому воркеру.
Замечание про `Atomic` корректно. Severity CRITICAL для safety-системы
оправдан.

### C-2 — checkpoint не трекает Retract/Update в offset — ПОДТВЕРЖДЁН, заведён как KI-1
Это тот же баг, что §4.1, в его более глубокой форме. Уже
задокументирован в `docs/known-issues.md` (KI-1, CRITICAL): на смешанных
потоках Data/Update/Retract при 2+ воркерах recovery рассинхронизирует
`cp_offset` со снапшотом. Эмпирически подтверждён property-тестом.
Корректный фикс затрагивает barrier-протокол и не закоммичен намеренно —
полу-рабочий фикс в exactly-once ядро класть нельзя. Статус без
изменений: открыт, честно зафиксирован.

### C-3 — keyed_join растёт без границ — ПОДТВЕРЖДЁН, ОТКРЫТ
`lib/pipe.ml:128` — `states : Hashtbl` без eviction. Watermark в
keyed_join (строка ~149) просто пробрасывается (`Some (Mf_event.wm wm)`),
очистки нет. Для контраста `dedup` (там же, ~353-358) корректно эвиктит
по watermark (`evict_before`). На неограниченном пространстве ключей
(device/session id, композитные ключи со временем) таблица растёт
бесконечно. Retract может обнулять slots, но сами ключи остаются.
Замечание верное; для join это серьёзное ограничение.

## HIGH

### H-1 — SPSC-контракт не enforced типами — РЕАЛЕН, осознанный дизайн
`variants/channel_v5.ml:23-28` — контракт SPSC задокументирован явно,
включая признание «не проверяется типами … footgun». Замечание точное.
Фантомные типы / раздельные producer/consumer-хэндлы действительно
устранили бы класс ошибок на этапе компиляции. Пока обеспечивается
топологией (dispatcher → worker, один пишет/один читает). Кандидат на
улучшение, не баг в текущем использовании.

### H-2 — supervisor теряет все Critical_failure кроме первого — ПОДТВЕРЖДЁН, ОТКРЫТ
`lib/supervisor.ml:81` — `if !crit = None then crit := Some (...)` хранит
только первый, остальные молча теряются. Плюс `List.iter Thread.join`
ждёт завершения всех пайплайнов перед re-raise — «отложенная»
критичность. Для системы, где первичный сбой требует немедленного
останова, это неправильно. Замечание верное.

### H-3 — window_fold: мутация Hashtbl во время итерации (UB) — ПОДТВЕРЖДЁН, ОТКРЫТ
`lib/window.ml:332` — `Managed_state.iter state (fun k _ ->
Managed_state.remove state k)`, то есть iter+remove, что по докам
стандартной библиотеки UB (может пропускать записи). Особенно
показательно: рядом в том же файле (строка ~182) уже есть правильный
паттерн collect-then-remove (`List.iter (Hashtbl.remove tbl)
!to_remove`), и `session_window` (~706) тоже делает правильно. Здесь —
нет. Замечание верное, фикс понятный.

### H-4 — Trigger.of_stream роняет Retract — РЕАЛЕН, осознанный дизайн
`lib/trigger.ml:429-432` — `Some (Mf_event.Retract _) -> next ()`,
Retract молча отбрасывается, с комментарием что это намеренно («триггер
реагирует только на свежие Data»). Это тот же паттерн, что мы уже
решали для `process_keyed` через опциональный `?on_retract` (по
умолчанию дропает — обратная совместимость). Здесь симметричное решение
напрашивается, но текущее поведение — сознательный выбор, не случайный
баг. Замечание про нарушение retract-контракта в комбинации с
retractable-операторами справедливо.

### H-5 — P2 quantile: точность после warmup — ДОКУМЕНТАЦИОННОЕ
`lib/agg.ml:144-152` — `dn = [0; 0.25; 0.5; 0.75; 1]`, `np = [1..5]`
инициализированы для n=5. Алгоритм корректен по Jain-Chlamtac; ревью
отмечает, что первые оценки после warmup (n≈6..30) менее точны, пока
маркеры не сошлись. Это известное свойство P2 — ревью само это
признаёт. Кода-бага нет; разумно лишь задокументировать ограничение
точности на ранней стадии.

## MEDIUM

### M-1 — dlq_log.count читает без mutex — ПОДТВЕРЖДЁН, тривиальный
`lib/dlq_log.ml:31` — `let count t = t.n` без mutex, тогда как `send`
его берёт. На OCaml 5 чтение int при конкурентной записи — UB. Фикс
тривиален (взять mutex и в count). Влияние — возможная неточность
финального счётчика DLQ.

### M-2 — Obj.repr/Obj.obj type erasure — СПОРЕН, требует внимания
`lib/managed_state.ml:94,130` — type-erased codec через `Obj.obj` /
`Obj.repr`. В заголовке модуля есть развёрнутое обоснование
безопасности (тот же codec того же namespace). Ревью верно отмечает: нет
runtime-проверки типа, и при случайном совпадении имён namespace два
оператора прочитают чужие байты как свой тип. Это реальный риск при
ошибке в namespace, хотя на практике namespace формируются из тегов
операторов. Замечание про различия immediate-значений OCaml 4/5 стоит
проверить отдельно.

### M-3 — per-epoch abort отбрасывает вклад живых воркеров — ПОДТВЕРЖДЁН, ОТКРЫТ
`lib/checkpoint_parallel.ml:363` — при крахе воркера `sink.ts_abort
(current_epoch)` откатывает буфер всей epoch (`buffered_sink`, ~268-278),
включая корректные результаты ещё живых воркеров той же epoch.
Правильно было бы per-worker rollback. Замечание верное; связано с
KI-1-зоной (barrier/epoch-протокол).

### M-4 — union: возможное переупорядочивание — СПОРЕН, требует теста
`lib/mf_event.ml:199-258`. При чтении кода защита есть: при двух pending
data берётся меньший ts (строка ~242), watermarks берут min, событие из
завершённого входа эмитится только когда другой пуст (`when !b_done`).
Сценарий ревью (один вход кончается high-ts событием, другой продолжает
low-ts) на вид обрабатывается корректно. Помечаю как требующий
прицельного property-теста, чтобы подтвердить либо опровергнуть.

### M-5 — count_sliding: трим по одному + дрейф since — СПОРЕН, требует теста
`lib/window.ml:506-509` — `if len > n then (… len - 1)` триммит один
элемент, но на каждом событии, поэтому буфер на практике не превышает
n+1. `since` считает шаги с последнего emit (не размер буфера), и при
триме не трогается — что согласуется с логикой шага. Дрейф emit-таймингов
из замечания требует проверки тестом на конкретных бёрстах.

### M-6 — snapshot: пик памяти 3x — ПОДТВЕРЖДЁН (как описано)
`lib/state_backend_memory.ml:11-12` — `Marshal.to_bytes (Hashtbl.fold …
list)`: оригинал + свёрнутый список + marshaled-байты дают ~3x пик на
каждом барьере. Замечание верное. Инкрементальный / copy-on-write
снапшот — корректное направление для больших состояний (есть в дорожной
карте README).

## LOW

### L-1 — Stream.split: буфер без границ — РЕАЛЕН, признан в дизайне
`lib/stream.ml:57-76` — очереди на потребителя без лимита/backpressure.
Ревью само отмечает, что это inherent и частично признано в комментариях.

### L-2 — max_ts=min_int: неточность метрики на старте — РЕАЛЕН (как описано)
`lib/runtime.ml:119,131` — `max_ts = ref min_int`, lag-метрика под
`if !max_ts > min_int` остаётся 0 до первого Data. Косметика мониторинга
на старте пайплайна.

### L-3 — temporal: история версий без auto-prune — РЕАЛЕН, есть ручной prune
`lib/temporal.ml:29-35` — `prune_versions_before` есть, но вызывается
вручную. Если забыть — рост без границ. Задокументировано в комментарии.

### L-4 — RocksDB: нет durability — ПОДТВЕРЖДЁН, ОТКРЫТ
`lib/rocksdb_stubs.c:55-60` — только `create_if_missing`. `set_sync` нет
нигде в файле. Для checkpoint-store, где важна durability на crash,
`rocksdb_writeoptions_set_sync(true)` оправдан. Замечание верное.

### L-5 — retry jitter при delay=0 — УЖЕ ИСПРАВЛЕН (ревью описывает старый код)
`lib/retry.ml:17-24` — в коде `if p.jitter && capped > 0 then Random.int
(capped + 1) else capped`. Защита `capped > 0` и `capped + 1` уже на
месте; `Random.int 1` из ревью в текущем коде отсутствует. Пункт
фактически неверен для актуального состояния.

## Самостоятельный аудит по классам (2026-06-30)

После триажа ревью проведён собственный adversarial-проход: каждый класс
дефекта из ревью прочёсан по всему коду — нет ли ещё таких же мест.
Найдено два места, которых в ревью не было.

### A-1 — trigger.ml: per-key Hashtbl без eviction — НОВОЕ, тот же класс что C-3
`lib/trigger.ml:230-231` — `states` и `last_event_ts` (per-key Hashtbl)
не имеют eviction: ни `remove`, ни watermark-очистки во всём файле. На
каждый новый ключ — постоянная запись. Это тот же класс утечки, что C-3
(keyed_join), но в триггерной системе; ревью его не отметило.

Острота для minePASS ниже, чем у keyed_join: ключ — id лампы (~4096
стабильных), поэтому таблица ограничена числом уникальных ламп за время
жизни пайплайна. На ротирующем/композитном пространстве ключей (сессии,
ключи со временем) — реальный неограниченный рост. Лечится так же, как
предлагается для C-3: watermark/TTL-eviction по аналогии с `dedup`.

### A-2 — runtime_context.ml: Obj.obj/Obj.repr — НОВОЕ, тот же класс что M-2
`lib/runtime_context.ml:58,62` — ambient-контекст хранится как `Obj.t`
(чтобы Ctx_store не зависел от типа контекста), приведение через
`Obj.obj`/`Obj.repr`. В заголовке есть обоснование (только этот модуль
кладёт/читает ячейку, поэтому namespace-коллизий как в managed_state
нет). Риск ниже, чем M-2, но замечание ревью про различие
immediate-значений (int/bool) между OCaml 4 и 5 применимо и здесь.

### Проверено и оказалось чисто (зафиксировано для честности)
Аудит не только нашёл новое, но и подтвердил отсутствие бага там, где он
мог быть — это важно не меньше:

- `checkpoint_parallel.ml` `alive[]` — синхронизирован под `co_mu`
  (запись в `mark_failed`, чтение в `try_close` — оба под мьютексом), в
  отличие от `failed[]`. Это показывает, что C-1 — точечный недосмотр, а
  не общая невнимательность к синхронизации.
- `fan_out.ml` `pending_accepted` — доступ из одного потока (pull в
  `advance`), не race.
- iter+remove по Hashtbl: из 7 совпадений 6 — корректный
  collect-then-remove (`item.ml`, `pipe.ml`, `table.ml`, `ttl_state.ml`,
  `window.ml:182,358`, `checkpoint_parallel.ml:282`, session-ветки
  `window.ml:717,795`). Реальное нарушение одно — H-3 (`window.ml:332`).
- `hash.ml` `mod n` — защищён `invalid_arg` при `n <= 0`.
- Крупные классы warning (partial-match, shadowing) ловятся сборкой
  (`-w +a-27-32-33-37-39-69-70`), поэтому в коде их нет.

### Границы аудита (чего он НЕ закрыл)
Честно о том, что осталось непроверенным:
- **Гонки на OCaml 5** проверены только чтением по модели памяти, без
  ThreadSanitizer — это не доказательство их отсутствия, только отсутствие
  очевидных. TSan-прогон с проводящим тестом — следующий шаг.
- **Утечки** найдены паттерн-матчингом (Hashtbl без remove), но не
  подтверждены ростом RSS на длинном soak именно для trigger/keyed_join.
- **Тонкая логика в редких ветках** (M-4 union, M-5 count_sliding)
  остаётся спорной — нужен прицельный property-тест, а не чтение.
